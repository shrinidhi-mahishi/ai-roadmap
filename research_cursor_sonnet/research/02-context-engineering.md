# Research: Context Engineering — Prompting, Context Management, Compression, Caching

**Date researched**: 2026-08-21
**Sources consulted**: 45

## 1. System Topology & Mechanics

### Control plane / data plane separation for context assembly
- Modern context-assembly pipelines separate a **control plane** (orchestrator/agent loop deciding what to fetch, summarize, or drop) from a **data plane** (the actual token stream sent to the model). Anthropic's framing: context engineering is "curating and maintaining the optimal set of tokens (information) during LLM inference," distinct from prompt engineering, which only concerns instruction wording. The control-plane logic runs the "compaction," "context editing," and "memory tool" decisions; the data plane is the literal request payload assembled just before the API call.
- Cursor implements this separation explicitly with **Priompt**, an open-sourced JSX-like prompt-compiler library: prompt components carry priority scores, and when total assembled context exceeds the model's token budget, a binary search drops the lowest-priority elements until the budget fits. This is a control-plane budgeting algorithm operating independently of the data plane (the final linear token string).
- Claude Code separates a "harness" control plane (compaction triggers, subagent dispatch, CLAUDE.md injection, hook execution) from the data plane (the literal message array sent to the model). The harness re-injects project-root `CLAUDE.md` files, auto-memory, and recent skill bodies into the data plane after every compaction event.

### Context-window budget allocation strategies
- Anthropic's engineering guidance frames the context window as a "finite attention budget" that must be allocated across: system instructions, tool definitions/schemas, MCP metadata, retrieved external data (RAG), and message/reasoning history — with the explicit goal of finding "the smallest set of high-signal tokens that maximizes the likelihood of your desired outcome," not maximizing window utilization.
- Cognition (Devin) names four concrete allocation levers: **Writing** (externalize state to files like `SUMMARY.md`/`CHANGELOG.md` instead of holding it in-context), **Compacting** (fine-tuned summarization models — Cognition found off-the-shelf summarizers dropped decision-critical details), **Isolating** (parallel sub-agents with separate context windows to avoid pollution), and **Selecting** (just-in-time loading of codebase data rather than upfront dumping).
- Claude Code's internal budget math (per community reverse-engineering of `autoCompact.ts`) reserves layered buffers: a **20K-token output reservation**, a **13K-token buffer**, and a **3K-token hard blocking limit** — three lines of defense so the model never silently overflows mid-generation.
> ⚠️ No vendor publishes an official universal formula for system/tools/history/RAG/scratchpad percentage splits; all concrete percentages above are framework-specific (Claude Code) or inferred from qualitative guidance, not published as a general standard. `[inferred]`

### Execution topologies for compression/summarization sub-pipelines (sync vs async)
- **Claude Code's three-tier compaction** is a canonical sync/async split:
  1. **MicroCompact** — synchronous, per-turn, surgically clears old tool results (~10–50K tokens reclaimed), can preserve cache via targeted "cache_edits" or force a full cache rebuild.
  2. **Session Memory Compact** — uses a continuously-maintained background-updated summary (async pre-computation) as the compaction payload, avoiding an LLM call at compaction time entirely.
  3. **Full Compact** — synchronous, blocking LLM call that summarizes the entire conversation; triggers at ~93% of effective context window (with "Context Collapse" pre-committing at 90% and hard-blocking at 95%); costs one full API round-trip and invalidates prompt cache.
- Cursor's embedding pipeline runs asynchronously in the background relative to the interactive edit loop: file changes are hashed via Merkle tree, and only changed chunks are re-embedded — decoupling the (slow) embedding step from the (fast) interactive query path.
- Anthropic's **context editing** (Claude Sonnet 4.5, public beta) automatically clears stale tool calls/results synchronously within the agent loop, without requiring a separate summarization LLM call — a cheaper, structural alternative to full summarization.

### Cache-aware prompt ordering and prefix-stability engineering
- Both OpenAI and Anthropic prompt caching require **exact prefix matches**: any token-level change earlier in the prompt invalidates the cache for everything after that point. Standard practice: place static content (system prompt, tool definitions, few-shot examples) first, and put variable/dynamic content (user query, session-specific data) last, including consistent ordering of tools and images across calls.
- Anthropic's cache billing partitions a request into ordered breakpoint segments — `A` (longest cache hit), `B` (highest 1-hour breakpoint after A), `C` (last cache breakpoint) — and separately bills a read for A, a 1-hour write for `(B−A)`, and a 5-minute write for `(C−B)`; this means breakpoint **ordering** in a request directly determines cost, not just presence.
- Known prefix-stability hazards (2026 production reports): image binary changes, `tool_choice` flips, session-resume re-seeding, and non-deterministic system-prompt construction (e.g., embedding timestamps or non-deterministic ordering of dict/set-derived content) silently invalidate the cache on every request even though the "intended" content is unchanged.
- vLLM's Automatic Prefix Caching (APC) and SGLang's RadixAttention operationalize this at the inference-engine level: APC hashes fixed-size KV blocks so any two requests sharing a prefix reuse the same physical memory; RadixAttention indexes at the token level via a radix tree, enabling variable-length prefix matches without block-alignment constraints (cache hit rates approach 95%+ for active multi-turn sessions).

## 2. Token Economics & NFR Metrics

### Latency SLA benchmarks for compression/summarization steps
- **LLMLingua** (Microsoft Research): end-to-end latency speedups of **1.7x at 2x compression, 3.3x at 5x compression, 5.7x at 10x compression** (measured on GSM8K, V100-32GB GPU). Achieves up to **20x compression** with claimed minimal performance loss; the paper explicitly cautions performance "plateaus and drops quickly" beyond ~20x, and that generation-length reduction (not prompt-token reduction) is the larger latency lever since output tokens dominate wall-clock time.
- **LLMLingua-2** is **3x–6x faster** than the original LLMLingua at the compression step itself (BERT-level encoder vs. small causal LM), targeting task-agnostic compression.
- **OpenAI prompt caching**: reduces time-to-first-token (TTFT) by **up to 80%**; empirically, cached requests were only 7% faster TTFT at 1,024 tokens but **67% faster at 150K+ tokens** — the latency benefit scales with prompt length.
- RAG retrieval-step latency budgets from a production wiki source: embedding server p50 5–20ms / p99 50–100ms (5s timeout); vector DB p50 2–10ms / p99 20–50ms (3s timeout); reranker p50 20–100ms / p99 200–500ms (10s timeout); LLM generation p50 500ms–5s / p99 5–15s (30s timeout).
- Long-context vs. RAG latency (Kimi K3 case study, 1M-token model): long-context queries took **~3x longer per question** than RAG even with partial prefix-cache hits (one question: 273.7s long-context vs. 46.3s RAG); another benchmark found long-context averaging 45s vs. RAG's ~1s per query.

### Token cost formulas: context bloat vs. compression, input/output splits
- **Anthropic prompt caching pricing multipliers** (stack on top of base input price): 5-minute cache write = **1.25x** base input; 1-hour cache write = **2.0x** base input; cache read = **0.1x** base input (a 90% discount vs. uncached input). Example (Claude Opus, $5/MTok base): 5-min write $6.25/MTok, 1-hour write $10/MTok, cache read $0.50/MTok, output $25/MTok.
- Break-even math for choosing 1-hour vs. 5-minute TTL (30K-token system prompt at $3/MTok input): 5-minute write ≈ $0.135, 1-hour write ≈ $0.169, each read ≈ $0.009 — **break-even at ~4 reads per write window**; 1-hour TTL wins whenever reuse cadence exceeds once per hour or gaps exceed 5 minutes.
- **OpenAI prompt caching**: automatic on prompts ≥1,024 tokens (GPT-4o and newer); pre-GPT-5.6 cache writes were **free**, reads discounted **50%** (later up to ~90% cost reduction and 80% latency reduction reported in later cookbook data); GPT-5.6+ introduces explicit **1.25x** write premium with **0.1x** read multiplier, mirroring Anthropic's model, and extends default TTL from "5–10 minutes, cleared within 1 hour" to a guaranteed **30-minute minimum**.
- **Google Gemini/Vertex AI context caching**: implicit caching (auto-enabled, Gemini 2.5+) gives a **90% discount** on cache hits with no code changes and no storage fee; explicit caching charges standard input rate for the initial cache-write plus an hourly **storage fee** (reported ~$1/MTok/hour) prorated to the minute, with TTL default 60 minutes (no fixed maximum).
- **Real-world cost blow-up case**: a March 2026 Anthropic regression silently dropped Claude Code's default cache TTL from 1 hour to 5 minutes; idle gaps ≥5 minutes forced a full 1.25x cold-cache-write on the entire conversation prefix (system + tools + CLAUDE.md + history) — on a 200K-token Opus session, a cold resume cost **~$1.25**, and across a working day this raised per-session cost **30–60%** without any application-level code change.
- **Elasticsearch Labs benchmark**: RAG achieved **~1,250x lower cost per query** than pure long-context prompting ($0.00008/request for RAG vs. $0.10/request for full-context), attributed to RAG's ~783 tokens/request vs. full-context's near-total-window consumption.
- LLMLingua's compute-savings formula: with a small compressor model at ~1/25th the parameter count of the target LLM and a 5x compression rate, the paper computes **~4x savings in computational resources** (derivation: total cost ≈ small-model overhead + compressed-inference cost, small-model FLOPs ≈ 1/25 of LLM FLOPs).

### Prompt/semantic caching mechanics — hit rates, TTL, invalidation
- **Anthropic**: default TTL 5 minutes (as of March 2026, down from a prior 1-hour default); optional 1-hour TTL via `cache_control: {"ttl": "1h"}`; sliding-window refresh — each cache hit resets the TTL clock; up to 4 breakpoints per request; minimum cacheable prefix 512–4,096 tokens depending on model; requires byte-for-byte prefix match.
- **OpenAI**: automatic, no configuration; minimum eligible prefix 1,024 tokens (some pre-GPT-5.6 models required up to 2,048 tokens); cache hits increment in 128-token steps; GPT-5.6+ supports explicit `prompt_cache_breakpoint` per content block and a fixed 30-minute TTL via `prompt_cache_options.ttl`; caches scoped at the organization level and not shared cross-org.
- **Google Gemini**: implicit caching minimum token floor varies by model — 2,048 tokens (Gemini 2.5 family), 4,096–6,144 tokens (Gemini 3 family); implicit-cache retention is based on load/reuse frequency and always cleared within 24 hours; explicit caches support TTL from 1 minute to unbounded.
- **vLLM Automatic Prefix Caching**: block-granularity (typically 16–32 tokens/block) hash-based reuse via a global hash table; supports `cache_salt` per-request to prevent timing side-channel attacks that could infer cached content across tenants; eviction is LRU on reference-count-zero leaf blocks — mathematically equivalent to RadixAttention's eviction policy for full-attention models.
- **SGLang RadixAttention**: token-level radix tree indexing gives automatic variable-length prefix matching without block-alignment loss; benchmarked **3–5x improvement in effective prefill latency** vs. vLLM on workloads with >60% prefix reuse; advantage disappears on fully unique-request workloads (e.g., creative generation).
- **GPTCache (open-source semantic caching)**: similarity-threshold gate on embedding cosine distance, configurable 0–1 (0 = no hits, 1 = all results returned as hits); typical production thresholds run **0.80–0.95** depending on domain (narrow FAQ: 0.90–0.95; technical support: 0.85–0.92; broad open Q&A: 0.80–0.88). A peer-reviewed GPT Semantic Cache study (arXiv 2411.05276) found threshold **0.80** optimal, reducing API calls by **up to 68.8%** with cache hit rates of **61.6–68.8%** and positive-hit accuracy **>97%**.

### Dynamic context-routing: summarize vs. truncate vs. RAG-retrieve
- The **SELF-ROUTE** method (ACL/EMNLP 2024, "RAG or Long-Context LLMs?") routes each query to either RAG or full long-context (LC) based on the model's own self-reflection about whether retrieval suffices. Findings: LC consistently **outperforms RAG on average when resourced sufficiently**, but predictions from LC and RAG are **identical for over 60% of queries** — for those, RAG can be substituted with no accuracy loss and major cost savings. SELF-ROUTE reduced cost by **65% for Gemini-1.5-Pro** and **39% for GPT-4o** while matching LC-level performance.
- Follow-on benchmark **LaRA** ("No Silver Bullet for LC or RAG Routing," 2025) found the optimal choice depends on model size, task type, and context length — reinforcing that routing must be dynamic/task-aware rather than a fixed global policy.
- Practical routing heuristic distilled from Redis/Meilisearch engineering blogs: prefer RAG when data volume vastly exceeds a single query's relevant subset, latency SLAs are tight, or updates are frequent; prefer long-context/full-stuffing when the corpus is small-to-moderate, static, and requires holistic cross-document reasoning with no infrastructure for chunking/embedding.

### Throughput: RPM/TPM impact of large contexts, batching implications
- Attention compute scales **quadratically (O(n²))** with sequence length; doubling context length roughly **quadruples** attention compute, contributing to reported latencies approaching minutes for very long contexts in production.
- **vLLM continuous batching**: allows new requests to fill freed batch slots every decode step (iteration-level scheduling) instead of waiting for full-batch completion; delivers **~2–3x throughput** over static/naive batching.
- **PagedAttention** (vLLM's memory-management scheme) eliminates KV-cache fragmentation from pre-allocation, enabling **2–4x more concurrent requests** on the same GPU memory footprint.
- **Chunked prefill** (`--enable-chunked-prefill`) splits long prompts across multiple scheduler iterations so a single long-context request cannot block decode progress for other concurrent users; reported to cut **P95 TTFT by 50–70%** on mixed short/long workloads, and vLLM's own docs report **P99 inter-token latency dropping from ~50ms to ~15ms** under mixed load.
- The `max_num_batched_tokens` (MBT) scheduler parameter is a pure latency/throughput tradeoff knob (not a model parameter): smaller values (~2,048) favor low inter-token latency; larger values (16,384+) favor better TTFT and raw throughput; no single static MBT is optimal across all load regimes (2026 arXiv paper "P-PAS: Prefill-Pressure Adaptive Scheduling").
- Combined optimizations (continuous batching + PagedAttention + chunked prefill) delivered **2,200–2,400 tok/s** for Llama 3.3 70B FP8 on 128+ concurrent requests on H100 SXM5 — roughly **3–4x** a naive PyTorch inference loop.

## 3. Distributed Resilience & State

### Durable execution patterns for long-running context/session state
- **LangGraph checkpointers** persist a full state snapshot at every "super-step" boundary, keyed by a `thread_id`; re-invoking with the same `thread_id` resumes execution from the last successful checkpoint. Two durability modes: `"exit"` (persist only on graph exit — best performance, no crash recovery mid-execution) and `"sync"` (persist before every step — full durability, added write overhead).
- LangGraph also persists **per-node (task-level) writes** within a super-step: if one node in a super-step fails, other nodes' already-completed writes are not re-executed on resume — task-level durability nested inside super-step-level checkpointing.
- Production guidance is explicit that `MemorySaver` (in-process) and even `SqliteSaver` are unsuitable for multi-instance production; `PostgresSaver`/`AsyncPostgresSaver` (or a Redis-backed saver) are required so state survives pod eviction, process restarts, and horizontal scaling.
- **MemGPT** (arXiv 2310.08560) formalizes an OS-inspired durable-state pattern: main context (analogous to RAM: system instructions + editable working context + FIFO message queue) vs. external context (analogous to disk: archival/recall databases). At a configurable "warning token count" (e.g., 70% of window) the queue manager injects a memory-pressure warning; at a "flush token count" (e.g., 100%) it evicts a set fraction (e.g., 50%) via recursive summarization into external storage — entirely self-directed by the LLM via function calls.

### Checkpointing of conversation/context state
- LangGraph's `aget_state_history()` allows paging through the full checkpoint history of a thread to reconstruct exact intermediate agent state at any point — used for both debugging and "replay with modified state" (patch a historical checkpoint via `update_state()` and re-invoke from that point rather than from scratch).
- Anti-pattern flagged in production LangGraph deployments: storing raw LLM responses (including usage metadata) directly in graph state causes checkpoint bloat — one reported case reached **180KB per checkpoint at 50 documents**, driving Postgres write latency to **400ms** and materially affecting response time; the fix was stripping state to only what downstream nodes actually consume.
- Claude Code's compaction telemetry emits three distinct events — `tengu_compact`, `tengu_compact_failed`, `tengu_compact_ptl_retry` — covering the success, failure, and retry paths of its checkpoint/compaction pipeline, illustrating an observability-first approach to context-state durability.

### Distributed locking for concurrent context mutation (multi-agent shared context)
- **Blackboard architecture** (from 1970s Hearsay-II speech-understanding systems) is the direct ancestor of the shared-scratchpad pattern in modern multi-agent LLM systems: independent specialist agents read/write a shared data structure without direct agent-to-agent calls, with a control component arbitrating write order ("opportunistic control").
- Two primary concurrency-control philosophies for shared agent state, per current (2026) engineering literature:
  - **Pessimistic distributed locking** — an agent acquires an exclusive lease (via Redis, ZooKeeper, or etcd) with a TTL before mutating shared state (e.g., a `StateGraph` or an MCP tool's target resource); TTL prevents deadlock if the lock-holder crashes. Redis's **Redlock** algorithm uses quorum consensus across multiple independent Redis nodes for safety.
  - **CRDTs (Conflict-free Replicated Data Types)** — each agent holds a local state replica and broadcasts deltas; the system provably converges without locks regardless of message arrival order, favored for higher-parallelism multi-worker scenarios (e.g., parallel browser-automation workers).
- Documented failure mode: **write oscillation** — two agents repeatedly overwrite each other's contribution to shared state in a loop because each interprets the other's write as requiring correction; mitigated by oscillation detection plus escalation to human review after N flip-flops.
- In distributed deployments, **circuit-breaker state itself must be centrally shared** (e.g., via Redis) — each process instance otherwise maintains independent breaker state, defeating the purpose of coordinated failure suppression across replicas.

### Circuit breakers for context-assembly failures
- Standard three-state circuit breaker (Closed → Open → Half-Open) applied to RAG-pipeline dependencies: **Closed** = normal traffic while failure rate is tracked; **Open** = trips after a failure threshold (e.g., 50% failures in 30s) and fails fast without attempting the call, giving the failing dependency room to recover; **Half-Open** = periodically allows a probe request to test recovery.
- Recommended per-service fallback behaviors when a circuit opens: embedding server down → fall back to keyword/BM25 search; vector DB down → return cached results or degrade gracefully (retrieval is otherwise impossible without a fallback); reranker down → skip reranking, use raw vector-similarity order; LLM down → return raw retrieved chunks with an explicit "generation unavailable" notice; knowledge graph down → skip enrichment, use pure vector retrieval.
- Recommended breaker tuning starting point: open after 3–5 consecutive failures, cool down 15–60 seconds, test recovery with 2 half-open probe requests.
- Retries, fallbacks, and circuit breakers are complementary, not substitutes: retries with exponential backoff + jitter handle transient blips; circuit breakers stop calling a service that is consistently (not transiently) failing; fallback chains (alternate provider, cached response, or degraded mode) execute once retries exhaust or the breaker is open.

### Rate-limiting fallbacks when context pipeline degrades
- Portkey/Bifrost-style LLM gateways implement automatic **fallback chains across providers/models** combined with circuit breakers that remove an unhealthy target from the routing pool for a fixed cooldown, preventing continued traffic to a degrading provider and preemptively activating fallback routes before retries fully exhaust (reducing tail latency during provider outages).
- Semantic caching itself functions as a degraded-mode rate-limiting fallback: when the primary generation path is circuit-broken, a Redis-backed semantic cache can serve a "good enough" previously-generated answer for a similar query rather than surfacing a hard failure.

## 4. Enterprise Security & Governance

### Zero-Trust considerations for context injected from external/untrusted sources
- OWASP's LLM Top 10 (2025) ranks **Prompt Injection as LLM01**, its top vulnerability, unchanged in rank since the 2023 list debut — reflecting a structural limitation: LLMs process instructions and data in the same token stream (the "semantic gap"), so untrusted context content can be misread as legitimate instructions.
- **Indirect (remote) prompt injection** specifically targets the context-assembly pipeline: malicious instructions are planted in content the LLM will later ingest as *data* — web pages, PDFs (including hidden white-on-white text), email bodies, code comments, commit messages, and even **MCP tool metadata/descriptions** (which are LLM-visible but not user-visible, per OWASP's AITG-APP-02 test guide).
- The **dual-LLM pattern** (Simon Willison, cited by OWASP) is the strongest architectural mitigation: a privileged LLM holds tool access but never reads untrusted content directly; a quarantined LLM reads untrusted content but cannot act; the privileged model receives only structured, sanitized summaries from the quarantined one, breaking the injection's path to action.
- **Spotlighting** (Microsoft Research, CEUR-WS paper) is a lighter-weight input-transformation defense with three instantiations of increasing effectiveness: delimiting (weakest), datamarking (recommended minimum), and encoding (e.g., base64 — most effective against injection but only viable with high-capacity models and only after quantifying its impact on downstream task accuracy).
- OWASP's layered defense-in-depth for context pipelines: **input screening** (classify user prompts *and* all retrieved/fetched context before the primary model sees it — pattern-based regex filters "do not reliably catch indirect injection"), **output screening** (score responses against policy before returning them, catching leaked system prompts or exfiltration markup), and **action screening** (evaluate proposed tool calls against original user intent using a guardrail that never saw the untrusted intermediate context, so it can catch intent-drift caused by injected instructions).

### Tool-level RBAC for what can be injected into context
- MCP's specification **does not define authorization** — this is an explicitly acknowledged gap that the community is filling with an "enterprise profile" proposal (tagging tools with sensitivity levels / required roles) and, in the interim, ad-hoc gateway proxies.
- The 2026 industry-standard pattern is a **gateway/proxy acting as Policy Enforcement Point (PEP)**: intercepts every MCP tool call, authenticates the caller (OAuth 2.1/OIDC — replacing static shared API keys with per-request identity), and queries a Policy Decision Point (OPA/Rego, Cedar, or vendor policy engines) before allowing execution. Decisions can be **allow / deny / escalate-to-human** (e.g., anything tagged `finance.write` or above a transaction threshold pauses for human approval).
- Concrete open-source implementation pattern (`mcp-zero-trust-proxy`): declarative RBAC roles (`admin`, `readonly`, `restricted`, plus unlimited custom roles) with `allowed_tools`/`deny_tools` lists, claim-based automatic role mapping from OAuth/OIDC claims (e.g., auto-assign "devops" role to the Engineering department), per-client session isolation, and per-client rate limiting (default reported: 60 req/min on free tier).
- NIST Zero-Trust principles as applied to agents: **mandatory authentication per request** (no cached permissions or long-lived sessions), **least-privilege scoping** (agents receive only the tool access their specific function requires), and continuous verification rather than one-time session trust.

### PII redaction within context/session logs
- **Microsoft Presidio** is the dominant open-source framework: an **AnalyzerEngine** (NER via spaCy + regex + checksum validators, e.g., Luhn-check for credit cards, + context-word confidence boosting) identifies PII spans with entity type, position, and confidence score; an **AnonymizerEngine** applies operators — `replace`, `mask` (preserve partial shape, e.g., last 4 digits), `redact` (full removal), `hash` (one-way, SHA-256 default), or `encrypt` (reversible, enabling controlled re-identification by authorized security/compliance staff).
- Standard enterprise "sandwich" architecture: proxy/gateway intercepts the prompt → Presidio anonymizes PII before it reaches the LLM (or its logs) → LLM processes the sanitized text → the proxy uses its stored (in-memory or encrypted) mapping to de-anonymize the *output* before returning it to the user, so the raw PII touches neither the model provider nor persisted logs.
- Explicit caveat from Presidio's own documentation: automated PII detection has **no guarantee of 100% recall** — it is risk *reduction*, not a compliance guarantee, and should be paired with additional review layers (e.g., a secondary local-LLM pass for edge cases like non-English names or unusual formats) plus continuous monitoring of detection counts (not the PII itself) to build eval sets for tuning.

### Sandbox isolation for context sources (web content, documents)
- Devin/Cognition's managed multi-agent pattern isolates each context source at the *execution environment* level: each managed sub-Devin runs in its own **isolated virtual machine** with its own terminal, browser, and dev environment, reporting back only a condensed summary — context pollution and any compromise from a malicious external source are contained to that VM rather than propagating into the coordinator's context window.
- Cursor's indexing pipeline enforces a sandboxing-adjacent privacy boundary rather than execution isolation: raw source code is **never persisted server-side**; only obfuscated file paths, line ranges, and embeddings are stored in Turbopuffer, and the client locally re-hydrates the actual text — reducing the blast radius if the server-side vector store were compromised.

### Structured audit logs for context provenance
- Enterprise MCP governance patterns record **every tool invocation as an immutable structured event**: tool name, arguments, server identity, session context, the policy version that evaluated the call, and the allow/deny/escalate decision — explicitly designed to answer "what did the agent do, and why was it allowed" for incident responders and auditors.
- Gateway products (Permit.io, mcp-zero-trust-proxy) log **who/what/where/when/decision** for every call and forward audit events to SIEM backends (Azure Sentinel/OCSF format, Splunk, CEF/syslog, or custom JSON webhooks) for unified security monitoring alongside non-AI infrastructure logs.
> ⚠️ No public vendor documentation was found specifying a standard schema for logging *the full context window contents* (as opposed to just the tool-call metadata) at the moment of a model's decision — most audit-log tooling captures tool invocations and policy decisions, not a snapshot of the complete assembled prompt. ## 5. Production Failure Modes

### Context window degradation ("lost in the middle") and context rot
- **"Lost in the Middle"** (Liu et al., TACL 2024, ACL Anthology 2024.tacl-1.9): across multi-document QA and key-value retrieval tasks, model accuracy follows a **U-shaped curve** — highest when the relevant fact sits at the very start or end of context, and degrades significantly when it sits in the middle, even for models explicitly marketed as long-context. Concrete measured accuracy across document position for one setup: **73.4% at index 0, 50.5% at index 9, 50.9% at index 14, 63.7% at index 29** — a ~23-point swing purely from position. Critically, adding the *correct* passage in a middle position sometimes performed *worse* than giving the model no external passage at all (closed-book baseline 56.1% vs. ~54% with the correct-but-buried passage).
- Extending the context window does not fix this: the paper found GPT-3.5-Turbo and GPT-3.5-Turbo-16K had **nearly identical accuracy-vs-position curves**, meaning the larger window only allowed more tokens to fit, not better mid-context reasoning.
- **"Context Rot"** (Chroma technical report, July 2025, authors Hong/Troynikov/Huber): tested **18 frontier models** (GPT-4.1, Claude Opus 4/Sonnet 4, Gemini 2.5 Pro, Qwen3 variants) across 5 controlled experiments holding task complexity constant while varying only input length. **Every single one of the 18 models degraded as input length increased**, well before hitting their advertised context-window limit. Key findings:
  - Degradation is **sharper when the needle and question are semantically (not lexically) similar** — i.e., harder, more realistic query phrasing accelerates rot.
  - Even a **single distractor** measurably lowers accuracy, with uneven effects across models.
  - Counterintuitively, **logically coherent haystacks produced worse performance than randomly shuffled ones** across all 18 models — flagged by the authors as deserving further research.
  - The **LongMemEval** conversational-QA experiment found a large accuracy gap between focused (~300-token) prompts and full-history (~113K-token) prompts, both well within the models' declared context windows.
  - The gap between marketed and *effective* (reliable) context length is large: on some task types the effective ceiling was reached **under 10K–50K tokens**, far short of 200K+ advertised windows.

### Infinite context-growth loops (unbounded history accumulation)
- LangGraph production guidance explicitly warns: "most agents fail in production because state grows unbounded" — every field in graph state gets fully serialized on every checkpoint write, so unpruned accumulation (e.g., storing full raw LLM responses with usage metadata) causes checkpoint size and write latency to grow without bound as a session lengthens (concrete case: 180KB/checkpoint at only 50 accumulated documents, pushing Postgres writes to 400ms).
- MemGPT's design explicitly treats this as the core problem it solves: without an eviction/paging mechanism, a FIFO conversation queue grows until it exceeds the "flush token count" (100% of window), at which point the system is forced into a disruptive full-queue flush rather than a graceful trim.

### State drift between compressed summaries and ground truth
- Cognition/Devin's engineering blog is explicit that generic, off-the-shelf summarization models **dropped decision-critical details** during compaction, motivating their investment in fine-tuned summarization models specifically for their own compaction pipeline — a direct acknowledgment that naive summarization introduces drift between the compressed representation and what actually happened.
- Claude Code's "Session Memory Compact" tier is designed around this risk: rather than re-summarizing from scratch at compaction time (introducing a new drift point on every compaction event), it substitutes a **continuously-maintained background summary** that is incrementally kept in sync with ground truth, reducing the number of discrete drift-introducing events.
> ⚠️ No public quantitative benchmark was found measuring summary-vs-ground-truth factual drift rate over N compaction cycles for any production agent framework. `[inferred]` This is treated qualitatively (as a known risk) rather than quantitatively in current public engineering literature.

### Cascading failures from context-assembly timeouts
- In RAG pipelines, an unprotected retrieval-step timeout (e.g., a hung vector-DB call) can cascade into full request failure if no circuit breaker or fallback is configured — the "vector DB down" fallback tier is explicitly flagged as the most severe degradation case ("significant — retrieval is impossible without a fallback") compared to reranker or knowledge-graph failures, which degrade more gracefully.
- The circuit-breaker literature explicitly frames the risk in agent loops: "repeated external calls could amplify [the] impact of a downed service" — an agent that retries a failing retrieval/context-source call on every loop iteration without a breaker can multiply load on an already-degraded dependency, worsening the outage it is trying to work around.

### Prompt injection via untrusted context content — real-world incident
- **Slack AI indirect prompt injection (disclosed August 2024 by PromptArmor)**: an attacker with any account in a Slack workspace posts crafted instructions in a **public** channel. When a victim with private-channel access later asks Slack AI a question, the AI pulls the attacker's planted public-channel text into its context window and follows the embedded instructions — which direct it to retrieve secrets (e.g., API keys) from private channels the attacker cannot access, and exfiltrate them by embedding the data inside a clickable Markdown link's URL parameters pointing to an attacker-controlled server. The victim only needed to click a plausible-looking "reauthenticate" link for the data to exfiltrate. A change on Slack's side (Aug 14, 2024) to have the AI also ingest **uploaded documents** widened the attack surface, since malicious instructions could now be hidden in PDF files (e.g., white-on-white text). Salesforce/Slack initially disputed the severity, then patched and publicly acknowledged the issue on Aug 21, 2024, stating no evidence of in-the-wild exploitation. Root cause, structurally: the AI's context-assembly pipeline had no boundary distinguishing "trusted instruction" from "retrieved data," allowing public, low-privilege content to steer a high-privilege retrieval action against private data — a textbook authorization break enabled purely by context-engineering failure (no input/output/action screening layer existed at the time).

## 6. Enterprise System Design Scenarios

### Real-world scale benchmarks for context pipelines

**Cursor** — full RAG + context-compilation stack:
- Codebase chunking via Tree-sitter at function/class boundaries (not arbitrary line counts); change detection via a **Merkle tree** of file hashes synced to servers every 5 minutes so only changed files are re-embedded; embeddings stored in **Turbopuffer** (serverless, object-storage-backed vector DB) with one namespace per codebase, active namespaces kept in memory/NVMe and inactive ones faded to object storage, warming on demand.
- Query-time reranking via a **fine-tuned 7B CodeLlama reranker** processing up to **500,000 tokens per query**, made "20x cheaper" via blob-storage KV caching (per third-party case-study analysis — not an official Cursor figure) `[inferred, secondary source]`.
- **Priompt**, Cursor's open-sourced prompt-compiler: JSX-like components carry per-element priority scores; when assembled context exceeds the token budget, lower-priority elements are dropped via binary search until it fits — treating prompt construction as a systems/compiler problem rather than string concatenation.
- Server never stores raw code — only obfuscated paths + line-range metadata; the local client re-reads actual code from disk to assemble the final prompt, which is also a security/privacy design choice (see Section 4).
- The agent has moved toward "dynamic context discovery": files are the unit of context management, and large/unwieldy outputs are written to temp files that the agent can choose to read, tail, or grep rather than being force-fed into context.

**Claude Code** — long-horizon session management:
- Three-tier compaction (MicroCompact → Session Memory Compact → Full Compact), described in detail in Sections 1 and 3.
- Full compaction (via Anthropic's public-beta **context editing** + **memory tool**, Sonnet 4.5) delivered a measured **39% improvement** on an internal agentic-search eval when combining both features, vs. **29% improvement from context editing alone** — Anthropic's own published benchmark.
- Community reverse-engineering reports **context editing reduced token consumption by 84%** while enabling a **100-turn web-search task** to complete (unverified secondary source, not an official Anthropic figure) `[inferred, secondary source]`.
- Subagents run in fully separate context windows (loading their own CLAUDE.md/MCP/skills configuration fresh, without the parent's conversation history), returning only a summary + small metadata trailer — the architectural mechanism for isolating large file reads from polluting the primary session.

**Devin / Cognition** — multi-agent isolation at VM granularity:
- "Managed Devins": a coordinator Devin decomposes a large task and delegates scoped pieces to child Devins, each running in its **own isolated VM** (own terminal, browser, dev environment), reporting back only condensed summaries; the coordinator can read full child trajectories to improve future task decomposition, monitor ACU (compute) consumption per child, and pause/terminate underperforming children.
- Cognition's explicit position (blog: "Don't Build Multi-Agents") is that multi-agent parallelism is a context-engineering tool of last resort with real costs: "parallelism burns through context ... which leads to context anxiety," and every agent action ideally needs visibility into all other agents' relevant decisions — a goal in direct tension with the context-window limits that motivate splitting work across agents in the first place.
- Cognition observed Claude Sonnet 4.5 is **the first model that is aware of its own context window** — it proactively summarizes progress and becomes more decisive about closing out tasks as it nears the limit, materially changing how Devin's harness needs to budget tokens (accounting for the model's own emergent summarization behavior, not just hard-coded compaction triggers).

### Trade-off matrix: full-context vs. RAG vs. compression vs. hybrid

| Approach | Cost | Latency | Accuracy | Best fit |
|---|---|---|---|---|
| **Full/long-context stuffing** | High — pay for every token in window on every call; no caching benefit if content changes turn-to-turn | High — attention is O(n²); Kimi K3 case showed 3–16x cost/latency vs. RAG on the same corpus | Strong on holistic/cross-document synthesis when context stays within the *effective* (not marketed) window; degrades via context rot beyond that | Small-to-moderate, static corpora; single-pass deep analysis; no retrieval infra available |
| **RAG (retrieval-augmented)** | Low — only relevant chunks enter context (~1,000x cheaper per Elasticsearch Labs benchmark) | Low — ~1s end-to-end typical vs. 30-60s+ for long-context on the same workload | Strong on narrow, well-retrievable facts; weak on tasks needing synthesis across many documents or poor retriever recall | Large/frequently-updated corpora; cost- and latency-sensitive interactive applications |
| **Prompt/context compression (LLMLingua-style)** | Moderate — added compressor-model inference cost, offset by reduced downstream token cost (up to 20x token reduction) | Net latency win at higher compression ratios (5.7x speedup at 10x compression) but adds a compression-step hop | Also **mitigates lost-in-the-middle** per LLMLingua's own claims, since compression increases signal density; quality plateaus/drops sharply beyond ~20x | High-volume, long-prompt pipelines (in-context learning, chain-of-thought, long RAG contexts) where prompts are reused across many calls |
| **Hybrid / dynamic routing (SELF-ROUTE, LaRA)** | Near-RAG cost on the ~60%+ of queries where RAG and LC agree | Near-RAG latency on routed-to-RAG queries | Near-LC accuracy overall — SELF-ROUTE matched LC performance at 65% lower cost (Gemini-1.5-Pro) / 39% lower cost (GPT-4o) | Production systems with heterogeneous query difficulty and cost sensitivity; requires self-reflection/routing logic overhead |

### Capacity planning data for context-heavy workloads
- GPU memory for KV cache is the binding constraint for concurrency at long context lengths; **PagedAttention** (2–4x more concurrent requests per GPU) and **prefix caching** (skips recomputation entirely for shared prefixes) are the two primary levers vendors use to plan capacity for context-heavy multi-tenant serving.
- Batching-parameter capacity planning: `--max-num-seqs` and `--max-num-batched-tokens` must be sized to actual workload sequence-length distribution and burstiness; **misconfigured conservative defaults (64 sequences / 2,048 batched tokens) can leave most GPU capacity unused** even under a long request queue — a common, easily-fixed production bottleneck.
- Google Cloud's Gemini optimization tiers illustrate capacity/latency/cost tradeoffs directly relevant to context-heavy batch workloads: Standard (full price, seconds-to-minutes), Flex (50% discount, best-effort/sheddable, 1–15 min target), Priority (75–100% cost premium, seconds, non-sheddable — for production user-facing apps), Batch (50% discount, up to 24h, for massive offline datasets/evals), and Caching (90% discount + prorated storage, fastest TTFT, for recurring queries over the same file) — a published, explicit topology for routing context-heavy workloads by urgency and reuse pattern.
