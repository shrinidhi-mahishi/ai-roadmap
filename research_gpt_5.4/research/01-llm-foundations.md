# Research: LLM Foundations — Transformers, reasoning, function calling, structured output

**Date researched**: 2026-08-21  
**Sources consulted**: 20

## 1. System Topology & Mechanics

- The original Transformer replaced recurrence and convolution with stacked self-attention plus feed-forward blocks, using a 6-layer encoder and 6-layer decoder in the canonical base architecture with `d_model=512`; decoder self-attention is explicitly masked so token generation remains autoregressive even though training-time attention is highly parallelizable. ([Attention Is All You Need](https://arxiv.org/abs/1706.03762))
- Self-attention reduces the path length between arbitrary token positions to a constant number of operations per layer, versus `O(n)` sequential steps for RNNs; this is the architectural reason modern LLM inference is usually described as "parallel prefill, serial decode." [inferred] ([Attention Is All You Need](https://arxiv.org/abs/1706.03762))
- Vaswani et al. reported `28.4` BLEU on WMT14 English-to-German and training in `3.5 days` on `8` P100 GPUs for the large model, establishing the baseline economic argument for transformer scaling: more parallel hardware utilization can outperform recurrence at lower wall-clock training time. ([Attention Is All You Need](https://arxiv.org/abs/1706.03762))
- In current API practice, function calling is an application-orchestrated control loop, not a self-executing model primitive: OpenAI defines a function as "a specific kind of tool" described by JSON Schema, and the application can continue the loop for as many tool calls as the task requires. ([OpenAI Function Calling](https://developers.openai.com/api/docs/guides/function-calling))
- Anthropic uses the same high-level pattern: tools are declared with `name`, `description`, and `input_schema`, with optional `strict`, `defer_loading`, and `allowed_callers` controls. That means tool dispatch is schema-mediated and runner-controlled rather than a direct capability of the base model. ([Anthropic Define Tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools))
- The practical control-plane/data-plane split in LLM systems is therefore: model chooses an action schema, application executes the action against external systems, then the result is fed back into the conversation. [inferred] ([OpenAI Function Calling](https://developers.openai.com/api/docs/guides/function-calling), [Anthropic Define Tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools))
- OpenAI Structured Outputs turns JSON Schema into a context-free grammar and masks invalid next tokens to probability zero during sampling; OpenAI reports `100%` reliability on its complex-schema evals for `gpt-4o-2024-08-06`, versus `<40%` for `gpt-4-0613`. ([Introducing Structured Outputs](https://openai.com/index/introducing-structured-outputs-in-the-api/))
- Anthropic's `strict: true` tool mode makes the same architectural move for tool inputs: schema-valid tool names and arguments are guaranteed by grammar-constrained sampling. ([Anthropic Strict Tool Use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use))
- Open-source serving stacks expose the same primitive more explicitly. vLLM supports constrained generation through `json`, `regex`, `choice`, `grammar`, and `structural_tag` modes and can auto-select among backends such as `xgrammar`, `guidance`, `outlines`, and `lm-format-enforcer`. ([vLLM Structured Outputs](https://docs.vllm.ai/en/latest/features/structured_outputs/), [vLLM Sampling Params Source](https://github.com/vllm-project/vllm/blob/main/vllm/sampling_params.py))
- Reasoning models add an additional planner-like stage inside the same turn. OpenAI states that reasoning models use internal reasoning tokens and can think between tool calls; Anthropic's thinking mode similarly surfaces special thinking blocks before tool use. ([OpenAI Reasoning Guide](https://developers.openai.com/api/docs/guides/reasoning), [Anthropic Extended Thinking with Tool Use](https://platform.claude.com/cookbook/extended-thinking-extended-thinking-with-tool-use))

## 2. Token Economics & NFR Metrics

- For production budgeting, the general cost formula is: `cost_per_1k_exec = 1000 * ((uncached_input * input_rate) + (cached_input * cached_input_rate) + (cache_write_input * cache_write_rate) + (output_tokens * output_rate)) / 1_000_000`. This is directly implied by OpenAI's separate billing categories for ordinary input, cached input, cache writes, and output. [inferred] ([OpenAI Prompt Caching](https://developers.openai.com/api/docs/guides/prompt-caching), [OpenAI Pricing](https://developers.openai.com/api/docs/pricing))
- OpenAI prompt caching has a hard minimum cacheable prefix of `1,024` tokens on GPT-5.6-and-later families, with cached reads billed at `0.1x` the uncached input rate and cache writes billed at `1.25x`; exact TTL is `30 minutes` when using `prompt_cache_options.ttl`. ([OpenAI Prompt Caching](https://developers.openai.com/api/docs/guides/prompt-caching))
- Anthropic pricing uses the same four-part structure for cached workloads. Current list pricing shows Claude Sonnet 5 at `$2/MTok` input, `$2.50/MTok` 5-minute cache writes, `$0.20/MTok` cache hits, and `$10/MTok` output; Claude Haiku 4.5 is `$1/$1.25/$0.10/$5` on the same dimensions. ([Anthropic Pricing](https://platform.claude.com/docs/en/about-claude/pricing))
- OpenAI's current pricing page shows `gpt-5.6-terra` short-context pricing at `$2/MTok` input, `$0.20/MTok` cached input, `$2.50/MTok` cache writes, and `$12/MTok` output; `gpt-5.6-luna` is `$0.20/$0.02/$0.25/$1.20`. That makes response-length control, not just prompt compression, a first-order cost lever. ([OpenAI Pricing](https://developers.openai.com/api/docs/pricing))
- A representative extraction workload of `2,000` input tokens and `400` output tokens costs about `$8.80` per `1,000` executions on `gpt-5.6-terra` with no cache hits, or about `$5.20` if all `2,000` input tokens are cache hits after warmup. [inferred] ([OpenAI Pricing](https://developers.openai.com/api/docs/pricing), [OpenAI Prompt Caching](https://developers.openai.com/api/docs/guides/prompt-caching))
- Reasoning tokens are economically important because they are invisible but billable: OpenAI states they occupy context-window space and are billed as output tokens, and recommends reserving at least `25,000` tokens for reasoning plus visible output while you characterize a workload. ([OpenAI Reasoning Guide](https://developers.openai.com/api/docs/guides/reasoning))
- Reasoning effort is an explicit latency/cost knob. OpenAI documents `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, and `max` as model-dependent settings, with lower effort favoring speed and token savings and higher effort favoring quality. ([OpenAI Reasoning Guide](https://developers.openai.com/api/docs/guides/reasoning))
- Anthropic documents a similar throughput reality from the opposite direction: Messages API quotas are split into `RPM`, `ITPM`, and `OTPM`, and a nominal `60 RPM` limit may be enforced as roughly `1 request/second`, so burstiness matters even when minute-level averages look safe. ([Anthropic Rate Limits](https://platform.claude.com/docs/en/api/rate-limits))
- OpenAI exposes rate dimensions as `RPM`, `TPM`, `RPD`, and `TPD`, plus response headers such as `x-ratelimit-limit-requests`, `x-ratelimit-limit-tokens`, and `Retry-After`; these headers are the primary runtime feedback channel for admission control. ([OpenAI Rate Limits](https://developers.openai.com/api/docs/guides/rate-limits))
- Public provider docs are strong on pricing and quota ceilings but weak on percentile latency.  
  > ⚠️ Limited public data available for p50/p95/p99 latency by model under production load; current primary sources mostly publish rate limits, pricing, and qualitative speed guidance rather than hard latency SLAs. ([OpenAI Rate Limits](https://developers.openai.com/api/docs/guides/rate-limits), [OpenAI Reasoning Guide](https://developers.openai.com/api/docs/guides/reasoning), [Anthropic Rate Limits](https://platform.claude.com/docs/en/api/rate-limits))

## 3. Distributed Resilience & State

- Raw LLM tool-calling APIs do not provide a documented built-in durable workflow engine comparable to Temporal; state durability is pushed to the application layer. [inferred] ([OpenAI Function Calling](https://developers.openai.com/api/docs/guides/function-calling), [Anthropic Define Tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools))
- What *is* explicit in provider docs is the minimum checkpoint contract. OpenAI requires that reasoning items returned alongside tool calls be passed back with tool outputs for reasoning models; lose them, and the next turn is no longer semantically equivalent. ([OpenAI Function Calling](https://developers.openai.com/api/docs/guides/function-calling))
- Anthropic is even stricter: when thinking is enabled, both `thinking` and `redacted_thinking` blocks must be preserved in conversation history, and modifying prior context can cause the API to reject the next request with `400`. ([Anthropic Extended Thinking with Tool Use](https://platform.claude.com/cookbook/extended-thinking-extended-thinking-with-tool-use))
- In practice, the natural checkpoint granularity for agent loops is the turn boundary immediately before and after each tool call, because that is where provider-visible state artifacts are emitted and must be replayed. [inferred] ([OpenAI Function Calling](https://developers.openai.com/api/docs/guides/function-calling), [Anthropic Extended Thinking with Tool Use](https://platform.claude.com/cookbook/extended-thinking-extended-thinking-with-tool-use))
- Structured output reduces one major recovery class: parser failure. OpenAI's CFG-based masking and Anthropic's strict tool mode shift retries from "invalid JSON" toward "valid schema, wrong business semantics," which is operationally much easier to classify and correct. [inferred] ([Introducing Structured Outputs](https://openai.com/index/introducing-structured-outputs-in-the-api/), [Anthropic Strict Tool Use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use))
- Anthropic's cache-aware quota model creates a concrete resilience lever: with `2,000,000` ITPM and an `80%` cache hit rate, Anthropic documents an effective `10,000,000` total input tokens/minute because cache reads do not count toward ITPM on most current models. ([Anthropic Rate Limits](https://platform.claude.com/docs/en/api/rate-limits))
- OpenAI recommends using `Retry-After` plus exponential backoff with jitter for temporary `429`s and notes that SDKs already honor these headers for eligible retries. This is the baseline circuit-breaker behavior that should sit underneath any higher-level agent retry policy. ([OpenAI Rate Limits](https://developers.openai.com/api/docs/guides/rate-limits), [OpenAI Error Codes](https://developers.openai.com/api/docs/guides/error-codes))
- Anthropic distinguishes steady-state limit exhaustion from acceleration limits; a sharp usage ramp can produce `429`s even below nominal ceilings. That makes load-shaping and warm ramp-up operational requirements, not optimizations. ([Anthropic Rate Limits](https://platform.claude.com/docs/en/api/rate-limits))
- Provider docs do **not** publicly describe internal leader election, lock managers, replay journals, or exactly-once semantics for hosted reasoning/tool loops.  
  > ⚠️ Limited public data available for provider-internal checkpoint engines, distributed locking, and replay semantics behind hosted tool-calling APIs.

## 4. Enterprise Security & Governance

- The MCP authorization spec provides the clearest primary-source blueprint for Zero-Trust tool connectivity. It requires OAuth `2.1`, requires MCP servers to publish OAuth Protected Resource Metadata (`RFC9728`), requires clients to use Resource Indicators (`RFC8707`), and requires PKCE with `S256` when technically capable. ([MCP Authorization Spec](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization))
- MCP servers can advertise authorization metadata through the `WWW-Authenticate` header or well-known URIs, and the resource metadata must include at least one `authorization_servers` entry. That is stronger than ad hoc bearer-token tool plugins because discovery, audience binding, and scope negotiation are standardized. ([MCP Authorization Spec](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization))
- OpenAI's API data controls state that abuse-monitoring logs may contain prompts/responses and are retained for up to `30 days` by default; approved customers can request Modified Abuse Monitoring or Zero Data Retention, and ZDR forces `store=false` for eligible `responses` and `chat.completions` calls. ([OpenAI Your Data](https://developers.openai.com/api/docs/guides/your-data))
- OpenAI also offers Enterprise Key Management / BYOK, with external key support through AWS KMS, Google Cloud KMS, and Azure Key Vault. ([OpenAI Your Data](https://developers.openai.com/api/docs/guides/your-data))
- Azure OpenAI states that prompts and responses are processed within the customer-specified geography unless Global/DataZone deployment types are used; content-filtering pipelines do not store prompts/completions for classifier training, and fine-tuning data is not used to train foundation models without customer permission. ([Azure OpenAI Data Privacy](https://learn.microsoft.com/en-us/azure/foundry/responsible-ai/openai/data-privacy))
- Azure also exposes a concrete governance flag: `ContentLogging=false` indicates abuse-monitoring storage is off for approved subscriptions. ([Azure OpenAI Data Privacy](https://learn.microsoft.com/en-us/azure/foundry/responsible-ai/openai/data-privacy))
- Tool-level authorization remains only partially provider-native. Anthropic exposes `allowed_callers` in tool definitions, and OpenAI supports restricting a run to an allowed subset of tools, but neither provider's basic function-calling contract is a full enterprise RBAC system with user-, tenant-, and resource-scoped policy evaluation. [inferred] ([Anthropic Define Tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools), [OpenAI Function Calling](https://developers.openai.com/api/docs/guides/function-calling))
- PII redaction, immutable audit storage, and per-tool approval workflows are still mostly integration responsibilities around the LLM call rather than intrinsic properties of transformer decoding or JSON-schema enforcement. [inferred] ([OpenAI Your Data](https://developers.openai.com/api/docs/guides/your-data), [Azure OpenAI Data Privacy](https://learn.microsoft.com/en-us/azure/foundry/responsible-ai/openai/data-privacy), [MCP Authorization Spec](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization))
- Public docs remain thin on the isolation substrate for hosted tool execution.  
  > ⚠️ Limited public data available for whether frontier vendors use containers, microVMs, process sandboxes, or WASM for all internal tool-execution paths; published material focuses more on auth, retention, and policy than on runtime isolation internals.

## 5. Production Failure Modes

- The most direct reasoning failure mode is silent token burn. OpenAI notes that if reasoning models hit the context-window limit or `max_output_tokens`, the response can return `status="incomplete"` before any visible output is produced, meaning you can spend input and reasoning tokens and still get no user-visible answer. ([OpenAI Reasoning Guide](https://developers.openai.com/api/docs/guides/reasoning))
- OpenAI's mitigation is concrete: reserve at least `25,000` tokens for reasoning and output when first tuning a workload, then trim once measured usage is known. ([OpenAI Reasoning Guide](https://developers.openai.com/api/docs/guides/reasoning))
- Structured output does not eliminate refusal handling. OpenAI explicitly states that a safety refusal may not follow the supplied schema and instead appears in a separate `refusal` field; downstream code must branch on that field rather than blindly deserialize. ([OpenAI Structured Outputs Guide](https://developers.openai.com/api/docs/guides/structured-outputs))
- Hallucinated tool parameters move from syntax errors to semantic errors under strict mode. `strict: true` on OpenAI and Anthropic guarantees schema conformance, but it does **not** guarantee that the chosen values are correct for the user's intent or authorized for the caller. [inferred] ([OpenAI Function Calling](https://developers.openai.com/api/docs/guides/function-calling), [Anthropic Strict Tool Use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use))
- State drift is a real multi-turn risk. OpenAI requires reasoning items to be passed back with tool results, and Anthropic rejects requests when prior thinking context is altered. If an orchestrator drops, truncates, or rewrites these artifacts during retries, the agent can diverge or fail hard. ([OpenAI Function Calling](https://developers.openai.com/api/docs/guides/function-calling), [Anthropic Extended Thinking with Tool Use](https://platform.claude.com/cookbook/extended-thinking-extended-thinking-with-tool-use))
- Long-horizon tool loops remain measurably brittle. BFCL's 2025 paper reports that while state-of-the-art models do well on single-turn calls, "memory, dynamic decision-making, and long-horizon reasoning remain open challenges." That is strong evidence for hard iteration caps, per-run cost budgets, and checkpoint/replay discipline in production agents. ([BFCL Paper](https://proceedings.mlr.press/v267/patil25a.html))
- Throughput failures often present as burst failures rather than sustained-average failures. Anthropic documents acceleration limits and short-interval enforcement; OpenAI documents `429`s with `Retry-After` and recommends jittered backoff. ([Anthropic Rate Limits](https://platform.claude.com/docs/en/api/rate-limits), [OpenAI Rate Limits](https://developers.openai.com/api/docs/guides/rate-limits))
- JSON mode is not enough when a bad tool argument can cause side effects. OpenAI explicitly distinguishes JSON validity from schema adherence; use strict structured outputs or strict function calling for any write path. ([OpenAI Structured Outputs Guide](https://developers.openai.com/api/docs/guides/structured-outputs))
- Public incident post-mortems specifically for frontier-provider tool-calling failures are still sparse.  
  > ⚠️ Limited public data available for detailed vendor post-mortems on reasoning-loop outages, tool-call corruption, or structured-output regressions.

## 6. Enterprise System Design Scenarios

- **Scenario A: deterministic document extraction service.** Use a smaller cost-efficient model with strict structured outputs, a reusable instruction prefix above the `1,024`-token cache threshold, and low/no reasoning effort. This minimizes parser failures and allows cache-read discounts to dominate cost. Good fit for high-volume ETL, claims intake, invoice parsing, and KYC normalization. ([OpenAI Structured Outputs Guide](https://developers.openai.com/api/docs/guides/structured-outputs), [OpenAI Prompt Caching](https://developers.openai.com/api/docs/guides/prompt-caching), [OpenAI Reasoning Guide](https://developers.openai.com/api/docs/guides/reasoning))
- **Scenario B: tool-augmented operations agent.** Use reasoning models for plan/tool/result loops, but persist the full turn transcript, tool outputs, and provider-specific reasoning artifacts after every tool call. Add max-iteration and max-cost guards because BFCL shows long-horizon reasoning is still an open problem. ([OpenAI Function Calling](https://developers.openai.com/api/docs/guides/function-calling), [OpenAI Reasoning Guide](https://developers.openai.com/api/docs/guides/reasoning), [Anthropic Extended Thinking with Tool Use](https://platform.claude.com/cookbook/extended-thinking-extended-thinking-with-tool-use), [BFCL Paper](https://proceedings.mlr.press/v267/patil25a.html))
- **Scenario C: regulated multi-tenant enterprise assistant.** Put an MCP/OAuth gateway in front of tools, bind tokens to resource servers via Resource Indicators, restrict tool visibility per tenant or role, and pair that with ZDR/BYOK or regional Azure processing controls depending provider choice. ([MCP Authorization Spec](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization), [OpenAI Your Data](https://developers.openai.com/api/docs/guides/your-data), [Azure OpenAI Data Privacy](https://learn.microsoft.com/en-us/azure/foundry/responsible-ai/openai/data-privacy))
- **Scenario D: open-weight structured-output gateway.** If you need custom grammars, regex-constrained output, or self-hosted latency control, serve via vLLM and choose the backend per request class (`json`/`grammar`/`regex`/`choice`). This increases operator responsibility but exposes more control than closed hosted APIs. ([vLLM Structured Outputs](https://docs.vllm.ai/en/latest/features/structured_outputs/), [vLLM Sampling Params Source](https://github.com/vllm-project/vllm/blob/main/vllm/sampling_params.py))
- **Trade-off summary.** Strict structured outputs materially improve correctness of machine-readable output; reasoning improves quality on hard tasks but increases hidden-token cost and incomplete-response risk; tool calling expands capability but introduces state, auth, and side-effect risk; caching is one of the few levers that improves both cost and throughput simultaneously. [inferred] ([Introducing Structured Outputs](https://openai.com/index/introducing-structured-outputs-in-the-api/), [OpenAI Reasoning Guide](https://developers.openai.com/api/docs/guides/reasoning), [OpenAI Prompt Caching](https://developers.openai.com/api/docs/guides/prompt-caching), [Anthropic Rate Limits](https://platform.claude.com/docs/en/api/rate-limits))
- **Capacity-planning heuristics.** For repetitive workloads, design prompts so the stable prefix crosses cache eligibility thresholds; for reasoning agents, budget explicit slack for hidden reasoning tokens; for tool agents, checkpoint at each tool boundary; for regulated workloads, treat tool execution and audit logging as separate security domains from model inference. [inferred] ([OpenAI Prompt Caching](https://developers.openai.com/api/docs/guides/prompt-caching), [OpenAI Reasoning Guide](https://developers.openai.com/api/docs/guides/reasoning), [OpenAI Function Calling](https://developers.openai.com/api/docs/guides/function-calling), [MCP Authorization Spec](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization))
