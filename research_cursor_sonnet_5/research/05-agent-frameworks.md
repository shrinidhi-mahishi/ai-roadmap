## 1. System Topology & Mechanics

### 1.1 LangGraph — Graph-Based State Machine

**Core primitives.** LangGraph models agent workflows as directed graphs built from three primitives: `State` (a shared data structure, typically a `TypedDict` or Pydantic model, that is the input/output schema for every node), `Nodes` (functions with signature `State -> Partial<State>` that encode agent/tool logic), and `Edges` (fixed or conditional functions that route execution between nodes). Each state key can carry an independent **reducer** function `(Value, Value) -> Value` controlling how concurrent node updates merge; if unspecified, updates overwrite. You build a graph with `StateGraph`, register nodes/edges, then call `.compile()` to produce an executable runtime supporting `.invoke()`, `.stream()`, `.ainvoke()` ([LangGraph Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api.md); [StateGraph Reference](https://reference.langchain.com/python/langgraph/graph/state/StateGraph)).

**Execution engine.** LangGraph uses a **Pregel-based** message-passing execution model (inspired by Google's Pregel graph-processing system) operating in transactional **supersteps** — when a node completes, it emits messages to successor nodes, which execute in the next superstep. This enables cycles, parallel fan-out/fan-in (via the `Send` API for map-reduce patterns), and dynamic control flow (via the `Command` API, which lets a node return both a state update and a routing decision in one object) ([Nodes/Edges Concepts](https://langchain-ai-langgraph-40.mintlify.app/concepts/nodes-edges)).

**Control/data plane separation.** State (data plane) flows through channels between nodes; routing logic (control plane) lives in conditional edges or `Command` objects, separate from the state schema itself. LangGraph explicitly supports mixing **deterministic, hand-coded steps with LLM-driven agentic steps in the same graph** — a distinguishing philosophy versus fully autonomous frameworks ([LangGraph Overview](https://docs.langchain.com/oss/python/langgraph/overview)).

**Topology.** Arbitrary directed graph (can be cyclic) — the most expressive topology of the four frameworks, at the cost of the steepest learning curve (1–2 weeks ramp-up cited by practitioners, vs. 2–4 hours for CrewAI) ([Uvik Software 2026](https://uvik.net/blog/agentic-ai-frameworks/)).

### 1.2 OpenAI Agents SDK — Code-First Agent/Handoff/Guardrail Model

**Core primitives.** Five primitives: `Agent` (LLM + instructions + tools, provider-agnostic though OpenAI is the default), `Handoff` (agent-to-agent delegation), `Guardrail` (input/output/tool safety checks with tripwires), `Tool` (function/hosted/computer/MCP/agent-as-tool), and `Tracing` (built-in OpenTelemetry-compatible observability). The `Runner` is the central orchestrator managing the turn loop, tool execution, guardrail evaluation, handoffs, and tracing ([Agent Architectures: OpenAI Agents SDK](https://agentarchitectures.com/framework/openai-agents-sdk)).

**The agent loop.** `Runner.run()` executes: (1) call the LLM for the current agent; (2) if output is `final_output`, terminate; (3) if the LLM emits a handoff (a `transfer_to_<agent_name>` tool call the model itself invokes), update the current agent and re-loop; (4) if the LLM emits tool calls, execute them, append results, and re-loop; (5) if `max_turns` is exceeded, raise `MaxTurnsExceeded` (or invoke a registered `error_handlers["max_turns"]` callback for graceful degradation) ([Running Agents Docs](https://openai.github.io/openai-agents-python/running_agents/); [Runner Reference](https://openai.github.io/openai-agents-python/ref/run/)).

**Handoffs vs. graph edges.** Unlike LangGraph's compiled edges or CrewAI's explicit process types, a handoff is a **tool call the LLM discovers and invokes at runtime** — control transfer is emergent from model reasoning, not statically compiled. By default the next agent inherits the **entire conversation history**; `input_filter` can prune/transform it. An opt-in beta (`RunConfig.nest_handoff_history`) compacts prior history into wrapped assistant-summary segments to control context growth across nested handoffs ([Handoffs Docs](https://openai.github.io/openai-agents-python/handoffs/); [Handoffs Reference](https://openai.github.io/openai-agents-python/ref/handoffs/)).

**Guardrails as infrastructure, not model behavior.** Input guardrails run only on the *first* agent in a chain; output guardrails only on the agent producing the *final* output; tool guardrails wrap individual function-tool calls. Guardrails can run in **parallel** (`run_in_parallel=True`, default — lowest latency, but the agent may burn tokens/side effects before the tripwire fires) or **blocking** (`run_in_parallel=False` — completes before the agent starts, preventing wasted spend) ([Guardrails Docs](https://openai.github.io/openai-agents-python/guardrails/)).

**Sandbox execution (April 2026).** The April 2026 update added native sandbox agents with persistent workspaces, manifest-defined mounts, and a model-native execution harness — elevating the SDK from "a wrapper around the Completions API" to a full execution environment ([TURION.AI Deep Dive](https://turion.ai/blog/framework-deep-dive-openai-agents-sdk/)).

**Topology.** Implicit, LLM-driven state-transition chain (not a compiled graph) — closer to a dynamically-routed linked list of agents than a topology with a fixed shape.

### 1.3 Google ADK — Event-Driven Runtime with Session/State/Memory

**Core primitives.** `Session` (a single ongoing conversation thread holding chronological `Events` and `State`), `State` (`session.state` — a scratchpad dict for data relevant to the current conversation only), `SessionService` (manages session lifecycle: create/retrieve/update/delete, and is the sole sanctioned path for persisting state changes via `append_event()`), and `Runner` (the primary entry point binding an agent to a session service and orchestrating the **event loop**) ([ADK Sessions Docs](https://github.com/google/adk-docs/blob/main/docs/sessions/index.md); [ADK State Docs](https://github.com/google/adk-docs/blob/main/docs/sessions/state.md)).

**Event loop mechanics.** ADK's runtime is a bidirectional **ask-yield** communication channel between the `Runner` and "Execution Logic" (Agents, LLM calls, Callbacks, Tools). State mutations made via `context.state[...]` inside a callback or tool are recorded locally in the `InvocationContext` but are only durably persisted once the generating code **yields** an `Event` carrying the `state_delta`, and the `Runner` processes it through the `SessionService`. Direct writes to `session.state` outside this flow are explicitly discouraged — only `CallbackContext`/`ToolContext`-mediated writes, `output_key`, or explicit `EventActions.state_delta` are considered safe ([Event Loop Docs](https://adk.dev/runtime/event-loop/); [The New Stack: ADK Architectural Tour](https://thenewstack.io/what-is-googles-agent-development-kit-an-architectural-tour/)).

**Multi-agent hierarchy.** A parent agent's `sub_agents` list establishes a tree (ADK auto-sets `parent_agent` on each child). Two orchestration mechanisms layer on top: (1) **Workflow agents** — `SequentialAgent` (shares one `InvocationContext` across sub-agents, enabling state-passing), `ParallelAgent` (distinct `InvocationContext.branch` per child, but a **shared** `session.state`, requiring distinct keys to avoid races), and `LoopAgent`; (2) **LLM-driven delegation** — a `CoordinatorAgent`'s `AutoFlow` mechanism transfers execution to sub-agents based on their natural-language descriptions, or a parent can wrap a sub-agent as an `AgentTool` for explicit, synchronous invocation ([ADK Multi-Agents Docs](https://github.com/google/adk-docs/blob/main/docs/agents/multi-agents.md); [Google Developer Blog: Multi-Agent Patterns](https://developers.googleblog.com/en/developers-guide-to-multi-agent-patterns-in-adk/)).

**Cross-service orchestration (A2A).** For agents running as independent services, ADK exposes an agent as an **A2AServer** and consumes remote agents via `RemoteA2aAgent`, which handles Agent Card discovery, authentication, and JSON-RPC messaging transparently — the closest of the four frameworks to a native "microservices for agents" pattern ([ADK A2A Intro](https://github.com/google/adk-docs/blob/5331a07f/docs/a2a/intro.md)).

**ADK 2.0 (stable May 19, 2026): graph-based Workflow Runtime.** ADK 2.0 replaced the 1.x hierarchical executor with a graph-based execution engine where Agents, Tools, and Functions are individually evaluated **nodes** — converging architecturally toward LangGraph's model. This is explicitly framed as a control-plane hardening measure: "even if an LLM node is manipulated, the workflow runtime lacks the pathways (edges or nodes) to execute unauthorized actions" ([Why We Built ADK 2.0](https://developers.googleblog.com/why-we-built-adk-20/); [ADK 2.0 Migration Docs](https://github.com/google/adk-docs/blob/main/docs/2.0/index.md)).

**Topology.** Hybrid: hierarchical tree (1.x) evolving to graph-based (2.0), with explicit A2A support for distributed, cross-service topologies.

### 1.4 CrewAI — Role-Based Crews with Sequential/Hierarchical Processes

**Core primitives.** `Agent` (role, goal, backstory — the persona scaffold prepended to every LLM call), `Task` (description, expected output, assigned agent, optional tools/context), `Crew` (orchestrator binding a list of agents and tasks under a `Process`), and `Process` (`sequential` | `hierarchical`, implemented as a type-safe enum) ([CrewAI DigitalOcean Guide](https://www.digitalocean.com/community/tutorials/crewai-crash-course-role-based-agent-orchestration); [CrewAI Processes Docs](https://docs.crewai.com/v1.15.1/en/concepts/processes)).

**Sequential process.** Tasks execute in list order; each task's output becomes context for the next. No dynamic branching without dropping to a custom process or wrapping in a `Flow`.

**Hierarchical process.** Requires a `manager_agent` or `manager_llm`. The manager dynamically creates/delegates tasks to agents based on their declared capabilities and validates outcomes — closer to an emergent, conversational orchestration model than a compiled graph. This flexibility is also CrewAI's most cited failure surface (see §5) ([CrewAI GitHub](https://github.com/crewaiinc/crewai)).

**Crews vs. Flows — the production bifurcation.** CrewAI explicitly separates two orchestration models: **Crews** optimize for autonomy and emergent collaboration (natural agent-to-agent delegation, flexible problem-solving); **Flows** are event-driven, production-grade workflows with fine-grained control, deterministic state management, and conditional branching, and can natively embed one or more Crews as steps. The documented production pattern is "prototype with Crews, harden with Flows around them" ([CrewAI GitHub](https://github.com/crewaiinc/crewai)).

**Topology.** Linear list (sequential) or star/hub-and-spoke with a manager (hierarchical) — the least expressive topology of the four natively, though `Flows` add graph-like control on top.

### 1.5 Cross-Framework Topology Summary

| Framework | Core abstraction | Topology | Control-flow driver |
|---|---|---|---|
| LangGraph | State + Nodes + Edges | Arbitrary directed graph (cyclic) | Compiled code (conditional edges / `Command`) |
| OpenAI Agents SDK | Agent + Handoff + Guardrail | Implicit chain, LLM-routed | Model-driven tool call (`transfer_to_X`) |
| Google ADK | Session/State + sub_agents + Workflow agents | Hierarchical tree → graph (2.0) | Mix of compiled workflow agents + LLM `AutoFlow` delegation |
| CrewAI | Agent + Task + Crew + Process | Linear list or manager hub-and-spoke | Manager LLM (hierarchical) or fixed order (sequential) |

## 2. Token Economics & NFR Metrics

### 2.1 Cross-Framework Token Benchmarks

A widely-cited 2026 benchmark ran **six frameworks** (LangGraph, LangChain AgentExecutor, AutoGen, CrewAI, Semantic Kernel, Haystack) through **five production-style tasks, 100 runs each**, pinned to GPT-4o to isolate framework overhead from model variance (2,000 total runs). Findings: LangChain was most token-efficient (~22% under the cross-framework median); **CrewAI consumed roughly 2× the tokens of the pack** on simple one-tool-call flows and ran several times slower; LangGraph's explicit state machine folded growing tool-call history back into context at every node, spiking to **~15,010 prompt tokens in a single call** on the heaviest, most branching task ([dreaming.press Token Cost Comparison](https://dreaming.press/posts/agent-framework-token-cost-comparison.html)).

A separate 2,000-run comparison (LangGraph, LangChain, AutoGen, CrewAI; five tasks × 100 runs) found: **LangGraph was fastest on latency across all five tasks**; LangChain was most token-efficient overall; AutoGen matched LangGraph's latency with a different token profile; **CrewAI carried the heaviest token footprint on simple tasks — roughly 3× the tokens of the other three frameworks** for one-tool-call flows ([Uvik Software 2026](https://uvik.net/blog/agentic-ai-frameworks/)).

**Root cause of CrewAI's overhead.** Every agent in a crew carries a `role`, `goal`, and `backstory` prepended to every LLM turn (~150 tokens of role scaffolding per agent per call in one measurement) — a 56% per-request overhead baked into the architecture. On a 3-agent pipeline at 10,000 requests/day (GPT-4o): **LangGraph ≈ $32/day** (developer-controlled prompts, ~800 tokens/request) vs. **CrewAI ≈ $50/day** (~1,250 tokens/request), an $18/day gap that compounds to **~$6,570/year** ([Markaicode LangGraph vs CrewAI](https://markaicode.com/vs/langgraph-vs-crewai-multi-agent-production/); [Decoded AI Tech](https://decodedaitech.com/langgraph-vs-crewai-40-of-agent-projects-still-fail/)).

**Hierarchical process tax.** CrewAI's `hierarchical` mode adds an extra LLM call per delegation decision — for 3 parallel tasks, 3 extra manager calls before work even starts, adding roughly 30% cost vs. sequential mode. Measured latency on a 3-parallel-agent task (GPT-4o, ~500 token outputs): **LangGraph ~4.2s**, **CrewAI hierarchical ~7.8s**, **CrewAI sequential ~13.1s** ([Markaicode](https://markaicode.com/vs/langgraph-vs-crewai-multi-agent-production/)).

**Orchestration overhead (routing decisions only).** Requesty's 2026 comparison found LangGraph spends "near zero" tokens on routing because it uses code (`if`/`else`, `match`) rather than LLM calls, while CrewAI spent **$4.10 in prompt tokens purely on orchestration** across 100 loop iterations of a standard research-and-summarize workflow — LangGraph used under 2,000 tokens/run on the same workload where CrewAI used ~4,500 ([Requesty SDK Comparison](https://www.requesty.ai/blog/best-ai-agent-sdks-compared-2026-langchain-crewai-openai-anthropic-google)).

> ⚠️ These benchmark numbers vary significantly by source and task type (simple vs. complex/branching), and none disclose full methodology/prompt templates — treat relative orderings (CrewAI > LangGraph in token cost on simple tasks) as more reliable than absolute percentages.

### 2.2 LangGraph-Specific Overhead

Independent measurement (GitHub issue, reproducible): a 16-turn ReAct agent with 65 messages produces a checkpoint of **21,850 bytes** under default `MemorySaver` full-Pydantic serialization, vs. **3,217 bytes** with a binary pooling serializer — an **85.3% storage overhead (6.79×)**. On the token side, the same 16-turn state serialized to the LLM context path costs **5,764 tokens** vs. **3,587 tokens** of true semantic content — a **37.8% token overhead paid every LLM call, every turn**. As of the report, there is **no pluggable serializer** at the checkpointer/store/stream/subgraph boundary ([LangGraph Issue #7714](https://github.com/langchain-ai/langgraph/issues/7714)). A maintainer rebuttal in the same thread disputes the token-overhead framing, noting checkpoint bytes never enter the LLM context directly (messages are rehydrated to provider wire format on resume) — flagging this as a contested claim.

### 2.3 OpenAI Agents SDK — Handoff Cycle Cost Amplification

Handoff cycles compound cost **non-linearly**: if Agent A hands to Agent B and B hands back to A, each cycle appends the accumulated context of prior cycles (A's context + B's context + A's context again), so **cycle 3 costs ~3× cycle 1**. A two-agent cycle with 5 handoffs each uses 10 turns — well under a `max_turns=20` cap that would appear "safe" — while costing **3–6× more** than the equivalent linear path, because `max_turns` counts LLM calls, not logical cycles ([RunGuard Cost Control](https://runguard.dev/blog/openai-agents-sdk-cost-control.html)).

**Transport-layer latency.** Default HTTP transport incurs per-call overhead (TCP/TLS handshake, header parsing) — measured at **~200ms overhead per tool-call round-trip** in a multi-hop workflow. Switching to a persistent WebSocket connection reduces per-message overhead to **~20ms**, yielding **30–50% total latency reduction** for agents with 3+ tool calls per run, and **40–60%** for tool-heavy workflows specifically ([CallSphere WebSocket Transport](https://callsphere.ai/blog/websocket-transport-low-latency-agent-communication)).

**Prompt caching.** OpenAI's automatic prompt caching applies to any prefix ≥1,024 tokens (GPT-5.6+: exact matching at explicit cache breakpoints + implicit caching; earlier models: automatic best-effort prefix reuse only). Cached input tokens bill at **0.1× the uncached rate**; tokens newly written to cache carry a **1.25× write-rate surcharge** (not stacked on top of a separate full charge); cache TTL is a 30-minute exact window (GPT-5.6+) or model-dependent retention (earlier models). Because Agent instructions/system prompts are typically stable across turns, they form a natural cache-eligible prefix in every framework built on the OpenAI API ([OpenAI Prompt Caching Docs](https://developers.openai.com/api/docs/guides/prompt-caching)).

### 2.4 Persistence Backend Overhead (LangGraph)

`SqliteSaver` adds **~2–5ms I/O latency per checkpoint write**, compounding across 10+ tool calls per workflow. Checkpoint storage grows **~2–4MB per workflow instance** in tool-heavy runs (web search + file read + code exec + enrichment); at 50 concurrent workflows this reaches **100–200MB in-memory** with `MemorySaver`/`SimpleCheckpoint` (which will OOM under sustained load) ([The Colony: Checkpoint Bloat](https://thecolony.cc/post/97ca6363-4d21-4862-aa67-782fbf71ff1f)).

### 2.5 Throughput / Concurrency Limits (Google ADK / Vertex AI Agent Engine)

Vertex AI Agent Engine (the managed ADK deployment target) enforces per-project quotas: `reasoning_engine_service_query_requests` (Query/StreamQuery calls per minute) and a hard cap of **10 concurrent `BidiStreamQuery` bidirectional connections per minute**. Google's own capacity-planning formula for a 250-peak-concurrent-user deployment at 2 requests/user/min: **base 500 QPM → recommended 750 QPM with a 50% buffer**; session-event-append quota scales at ~12 events per query (tool call → LLM → tool response → final response chain), i.e., 500 QPM → 6,000 events/min base → 9,000 with buffer ([Google Cloud Agent Quotas](https://docs.cloud.google.com/gemini-enterprise-agent-platform/resources/agent-quotas)). Undersized quotas surface as `429 RESOURCE_EXHAUSTED`, sometimes mis-reported as a generic `500` during streaming — a documented operator-visibility gap ([ADK Issue #4323](https://github.com/google/adk-python/issues/4323)).

## 3. Distributed Resilience & State

### 3.1 LangGraph — Checkpointers, Stores, and the Durability Spectrum

**Two-tier persistence.** **Checkpointers** persist a thread's graph state as versioned checkpoints (short-term, thread-scoped memory: conversation continuity, human-in-the-loop, time-travel debugging, fault tolerance). **Stores** persist application-defined key-value data outside the graph state (long-term, cross-thread memory: user preferences, shared facts) ([LangGraph Persistence Docs](https://docs.langchain.com/oss/python/langgraph/persistence)).

**Durability modes.** Three explicit modes trade latency for durability: `"exit"` (checkpoint only at graph completion — fastest, zero mid-run crash recovery), `"async"` (persisted asynchronously during the next step — small window of loss on crash; **this is the default**), `"sync"` (persisted before advancing to the next step — highest durability, recommended for production) ([dreaming.press: Checkpointing vs. Temporal](https://dreaming.press/posts/langgraph-checkpointing-vs-temporal-durable-execution.html)).

**Backend tradeoff.** `PostgresSaver` is the first-party production default — checkpoints are permanent rows queryable via `get_state_history()`, enabling audit, HITL review, and forking/replay from any prior checkpoint ("time travel"). `RedisSaver` (maintained by Redis, not LangChain core) trades permanence for speed and **TTL-based auto-expiry** — ideal for high-churn, short-lived conversational threads with no long-term audit need; it depends on RedisJSON/RediSearch modules (bundled in Redis 8.0+). Rule of thumb: "if state history is an asset, use Postgres; if resume speed and auto-expiry matter more than permanence, use Redis. Never ship `MemorySaver`" ([dreaming.press: Postgres vs. Redis](https://dreaming.press/posts/langgraph-checkpointer-postgres-vs-redis.html)).

**Checkpoints are not durable *execution*.** A critical distinction: LangGraph checkpoints preserve *data* between node boundaries, not a journal of what happened *inside* a node. If a node crashes mid-execution (e.g., after issuing a refund API call but before returning), resume **re-enters and re-runs the entire node from the top** — LangGraph's own docs state plainly: "assume nodes re-execute on resume." The `@task` primitive mitigates this for non-idempotent side effects by caching the task's result so a replay returns the cached value instead of re-invoking the API ([dreaming.press: Checkpointing vs. Temporal](https://dreaming.press/posts/langgraph-checkpointing-vs-temporal-durable-execution.html)).

**Temporal + LangGraph integration.** The official Temporal LangGraph plugin runs the compiled graph as a Temporal Workflow, with each node/task optionally executing as a Temporal Activity (with configurable timeouts/retries) or inline (must stay deterministic). This shifts durability ownership from application code to the runtime: a model-call timeout, tool error, or full machine failure mid-run is retried per policy and the graph resumes from durable state on the same or a different worker — closing the "single-process ceiling" of vanilla LangGraph. `interrupt()` calls become **durable waits** (a human can respond in an hour or a month at zero holding cost) rather than an open process burning compute. Caveat: LangGraph's in-memory `Store` is unavailable inside Activity-wrapped nodes, since live graph state cannot cross the Activity boundary — memory needing survival must be modeled as durable state, not node-local storage ([Temporal Blog: LangGraph Plugin](https://temporal.io/blog/temporal-langgraph-plugin-durable-execution)).

### 3.2 Google ADK — Session, State, and Memory Services

ADK cleanly separates three concerns: **`Session`** (single-conversation event history + scratchpad state), **`SessionService`** (lifecycle manager: create/retrieve/append/delete — the only sanctioned path for durable persistence), and **`MemoryService`** (long-term, cross-session knowledge retrieval). In-memory implementations of both services exist for local dev/testing but **lose all data on process restart**; production deployments use Cloud Firestore, PostgreSQL, or the managed Vertex AI Agent Engine Sessions + Memory Bank service ([ADK Sessions Docs](https://github.com/google/adk-docs/blob/main/docs/sessions/index.md); [The New Stack](https://thenewstack.io/what-is-googles-agent-development-kit-an-architectural-tour/)).

**Migration/versioning friction.** ADK 1.x and 2.0 session schemas are **structurally incompatible** — 2.0 can read legacy pickle-based v0 schemas with deprecation warnings but requires migration to the JSON-based v1 schema for long-term support. Google explicitly flags cross-version storage sharing as **data-loss territory**: "back up production session data, run 1.x and 2.0 in completely separate storage environments, plan a migration window, not an in-place upgrade" ([DEV Community: ADK 2.0 Migration](https://dev.to/peytongreen_dev/google-adk-20-is-now-stable-workflow-runtimes-breaking-changes-and-how-to-migrate-4ah8)). There is an open, unresolved RFC (as of mid-2026) requesting Alembic-based schema migrations, citing breaking schema changes across ADK 1.14.0/1.17.0/1.19.0 with no automated migration path, no Kubernetes-native migration hooks, race conditions when multiple pods migrate concurrently, and no rollback capability ([ADK Issue #4387](https://github.com/google/adk-python/issues/4387)).

### 3.3 OpenAI Agents SDK — Pluggable Session Backends

Sessions automatically persist and prepend conversation history across `Runner.run()` calls keyed by `session_id`, eliminating manual `.to_input_list()` management. Backend options span the full production spectrum: `SQLiteSession` (local/simple apps, file- or memory-backed, thread-local connections with file-locking for concurrent access), `AsyncSQLiteSession` (async driver), `RedisSession` (shared memory across distributed workers, TTL support, `from_url()` construction), `SQLAlchemySession` (any SQLAlchemy-supported DB), `MongoDBSession` (atomic sequence counters for ordering across processes), `DaprSession` (cloud-native sidecar pattern with pluggable state stores), `OpenAIConversationsSession` (server-managed by OpenAI), `OpenAIResponsesCompactionSession` (auto-compaction wrapper for long conversations), `AdvancedSQLiteSession` (branching + per-turn token usage analytics), and `EncryptedSession` (encryption + TTL wrapper composable over any backend) ([OpenAI Agents SDK Sessions Overview](https://openai.github.io/openai-agents-python/sessions/)).

### 3.4 CrewAI — Unified Cognitive Memory

CrewAI replaced four separate memory types (`ShortTermMemory`, `LongTermMemory`, `EntityMemory`, `ExternalMemory`) with a single **unified `Memory` class** built around five "cognitive operations": encode, consolidate, recall, extract, forget. On save, an LLM infers scope/categories/importance; on recall, a multi-step `RecallFlow` assesses query complexity and confidence, deepening search (`depth="deep"`, default) or using fast vector-only search (`depth="shallow"`, ~200ms, no LLM call). Retrieval uses **composite scoring**: `semantic_weight × similarity + recency_weight × decay + importance_weight × importance`. A `ConsolidationFlow` on save detects and merges near-duplicate records. Default embeddings are OpenAI `text-embedding-3-large` (3072-D); custom embedders are configurable ([CrewAI Memory Docs](https://docs.crewai.com/en/concepts/memory); [CrewAI PR #4420: Unified Memory](https://github.com/crewAIInc/crewAI/pull/4420)). Storage backend moved to `LanceDBStorage`. Memory attaches to a single `Agent`, a `Crew` (shared across all member agents unless overridden), or a `Flow` (as a first-class `self.remember()`/`self.recall()` capability, complementing `Flow` state which is explicitly ephemeral-per-run vs. memory which compounds across runs) ([CrewAI Cognitive Memory Blog](https://crewai.com/blog/how-we-built-cognitive-memory-for-agentic-systems)).

> ⚠️ CrewAI memory has a documented degenerative failure mode: one production user reported that repeated re-runs after 429 rate-limit errors caused agent memory to progressively **degrade output quality into hallucination**, with no built-in way to select a memory "start point" or partially reset — the only workaround found was deleting the entire local memory store ([CrewAI Issue #826](https://github.com/crewAIInc/crewAI/issues/826)).

### 3.5 Rate Limiting, Circuit Breakers & Distributed Locking (Cross-Framework Patterns)

None of the four frameworks ship a built-in **multi-agent-aware** rate limiter or distributed lock manager natively — these are consistently implemented as an external layer:

- **Centralized quota coordination.** Production guidance converges on a shared **Rate Governor / token-bucket-per-identity** pattern: a Redis-backed (or file-locked, for single-node) global counter that all agents consult before calling the LLM API, with reservation semantics (agents request quota before starting a task) and quota reclamation for unused reservations ([Fast.io Rate Limiting](https://fast.io/resources/ai-agent-rate-limiting/); [Tamir Dresher: 9 Agents One Quota](https://www.tamirdresher.com/blog/2026/03/21/rate-limiting-multi-agent)).
- **Multi-tenant isolation.** Bucket keys should include a `tenant` dimension — `(tenant, workload, model)` — so one tenant's runaway agent throttles only that tenant, with a platform-wide breaker as backstop ([TrueFoundry: 3-Layer Gateway](https://www.truefoundry.com/blog/rate-limiting-ai-agents-preventing-llm-api-exhaustion)).
- **Circuit breakers should be predictive, not just reactive.** A "Predictive Circuit Breaker" pattern monitors cost/error velocity (e.g., request rate climbing from 1 req/s to 110 req/s in two minutes) and **gracefully downgrades** (e.g., switch to a cheaper model) rather than hard-failing after the fact ([Tamir Dresher](https://www.tamirdresher.com/blog/2026/03/21/rate-limiting-multi-agent)). Standard SRE circuit-breaker semantics apply: track error rate over a sliding window, open the circuit above a threshold (e.g., >10% errors), half-open after a cooldown, close on a successful probe ([Fast.io](https://fast.io/resources/ai-agent-rate-limiting/)).
- **Distributed locking / idempotency fencing.** For non-idempotent tool calls (payments, emails), the correct pattern is an atomic **claim-before-execute** in durable storage *outside* the graph/session state: derive a stable `request_id` from tool arguments (not attempt metadata), atomically insert a `PENDING` record before execution (Redis `SET NX` / Postgres unique constraint), and have redispatched retries resolve against the stored receipt instead of re-executing. This directly addresses LangGraph's documented long-tool-call re-dispatch bug (§5) ([LangGraph Issue #7417](https://github.com/langchain-ai/langgraph/issues/7417); [fencekit](https://github.com/ahmed5145/fencekit)).
- **OpenAI Agents SDK-specific cost circuit breaker.** Because `max_turns` counts LLM calls, not logical agent-to-agent cycles, a purpose-built wrapper (`RunGuard`) intercepts `Runner.run()` via `RunConfig` hooks to detect handoff pair-repetition within a sliding window (`cycle_window`, tunable 4–12) and a **cost-drift breaker** (open the circuit if the last 3 turns average >2.5× the cost of the first 3 turns) — catching cost blowups the native `max_turns` limit misses entirely ([RunGuard](https://runguard.dev/blog/openai-agents-sdk-cost-control.html)).

## 4. Enterprise Security & Governance

### 4.1 OpenAI Agents SDK — Guardrails and Human-in-the-Loop Approvals

Guardrails are explicit programmatic checks (LLM-powered reasoning agents *or* deterministic rule-based/regex functions) that set a `tripwire_triggered` boolean on a `GuardrailFunctionOutput`. When triggered, the SDK raises a typed exception — `InputGuardrailTripwireTriggered`, `OutputGuardrailTripwireTriggered`, `ToolInputGuardrailTripwireTriggered`, `ToolOutputGuardrailTripwireTriggered` — and halts execution immediately, with the exception object exposing every guardrail result accumulated before the trip for forensic/audit purposes ([Guardrails Reference](https://openai.github.io/openai-agents-python/ref/guardrail/)). Separate from guardrails, **human-in-the-loop approvals** pause a run before side effects like cancellations, edits, shell commands, or sensitive MCP tool actions — a distinct decision point ("should this run continue/pause/stop") from automatic guardrail validation ([OpenAI Guardrails & Human Review Guide](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals)). For authorized security-testing workflows, OpenAI's own guidance recommends evaluating every sensitive tool call against an approved engagement scope at the point of side effect, denying out-of-scope hosts/credential theft/persistence/data exfiltration by default, and pausing ambiguous or high-risk actions for explicit human approval.

**Recommended cost/security pattern.** Run a cheap/fast model (e.g., `gpt-4o-mini`) as the input guardrail to filter malicious or off-topic queries in **blocking mode** before invoking the expensive primary agent — described by practitioners as "production-ready... we recommend it for any customer-facing agent" ([TURION.AI Deep Dive](https://turion.ai/blog/framework-deep-dive-openai-agents-sdk/)).

**Sandboxing.** The April 2026 update added native sandboxed execution with isolated file systems and manifest-defined mounts for agents that write code or process files, closing a prior gap where developers had to build their own execution harness ([niteagent.com Production Guide](https://niteagent.com/blog/openai-agents-sdk-production-guide-2026/)).

### 4.2 Google ADK — Callback-Based Governance Plugins

ADK's security model is built entirely on **interception hooks** at four lifecycle points: `before_model_callback` (inspect/block requests before they reach the LLM; returning a non-`None` `LlmResponse` skips the LLM call entirely — the mechanism for guardrails and caching), `after_model_callback` (inspect/sanitize raw model output), `before_tool_callback` (validate tool arguments, perform authorization checks; returning a dict skips tool execution and uses the dict as the result), `after_tool_callback` (sanitize tool results before they re-enter model context, or route large payloads to session state instead of the context window — the **"store-and-slim" pattern**) ([ADK Callback Types Docs](https://github.com/google/adk-docs/blob/main/docs/callbacks/types-of-callbacks.md); [Ayush Mittal: Callbacks Guide](https://ayushm4489.medium.com/taming-the-agent-a-practical-guide-to-callbacks-in-google-adk-831b2f017c6f)).

**Critical gap: callbacks are opt-in, not enforced.** A CISO-focused audit bluntly states: "the security gap in most ADK deployments is treating these callbacks as optional. They are not registered by default, and the framework will execute without them. Teams that deploy ADK without callback-based controls are running agents without any runtime guardrail layer" ([BeyondScale CISO Guide](https://beyondscale.tech/blog/google-adk-security-ciso-enterprise-guide)).

**Callbacks vs. Plugins.** Callbacks are simple, per-agent — ideal for one-off guardrails. **Plugins** are the recommended mechanism for policies that must apply consistently across many agents: self-contained, modular, registered once at the `Runner` level, applied globally without per-agent repetition ([ADK Safety Docs](https://adk.dev/safety/)).

**PII redaction pattern.** Recommended implementation: `before_tool_callback` runs PII detection (e.g., via Microsoft Presidio) on tool inputs/outputs and blocks calls that would send PII to services not cleared for that data class; a governance plugin's `before_model_callback` redacts detected PII (e.g., replacing "John Doe" with `[PERSON_NAME]`) so the sanitized prompt — never the raw PII — reaches the LLM and is logged, with a `pii_redacted: true` audit tag ([Sravan Gottipaty: Guardrails & Logging Part 2](https://medium.com/@sravan.gottipaty/part-2-0-collect-before-you-score-guardrails-logging-for-your-adk-agents-e7ed20c75fe8)).

**Sandboxed code execution.** ADK integrates with Vertex Gemini Enterprise API server-side sandboxed `tool_execution`, or the Vertex Code Interpreter Extension for data-analysis workloads ([ADK Safety Docs](https://adk.dev/safety/)).

**Audit logging minimum bar.** Recommended minimum forensic log entry per tool call: sanitized input parameters, allow/block decision, status, downstream resource URI, latency — sufficient to reconstruct an agent's actions after a suspected compromise ([BeyondScale](https://beyondscale.tech/blog/google-adk-security-ciso-enterprise-guide)).

### 4.3 LangGraph — Persistence-Layer Audit Trail

LangGraph's Postgres-backed checkpointer functions as an incidental but powerful audit mechanism: `get_state_history()` provides a **full, queryable ledger** of every graph state transition per thread, enabling "why did it decide that" forensic review and time-travel replay from any historical checkpoint — a first-class capability, not a bolt-on ([dreaming.press: Postgres vs. Redis](https://dreaming.press/posts/langgraph-checkpointer-postgres-vs-redis.html)). LangGraph itself does not ship dedicated RBAC/PII-redaction primitives; these are typically layered in as custom nodes or middleware around the `interrupt()` human-in-the-loop primitive.

### 4.4 CrewAI — Enterprise Platform (AMP) Security

CrewAI's enterprise offering ("Agent OS" partnerships, e.g. with PwC) emphasizes **RBAC and secure key management across frameworks and cloud providers**, native **Model Context Protocol (MCP)** support for scoped agent access to corporate data stores, and native **Agent-to-Agent (A2A)** protocol support for cross-framework interoperability — positioned as the "only one with native A2A support" among the compared frameworks in at least one analysis ([CrewAI: PwC Agent OS](https://crewai.com/blog/pwc-choses-crewai-to-help-power-theirglobal-agent-os); [tokenmix.ai Comparison](https://tokenmix.ai/blog/agent-frameworks-2026-langgraph-crewai-autogen-openai-sdk)). Open-source CrewAI itself does not ship built-in PII redaction or guardrail primitives comparable to OpenAI SDK's guardrails or ADK's callbacks — security is delegated to the enterprise platform layer or custom tool wrappers.

### 4.5 Cross-Cutting: Zero-Trust Agent Identity (Framework-Agnostic)

Independent of the four frameworks, 2026 enterprise practice converges on an **Agent Access Model**: every agent gets a unique, cryptographically-rooted identity (no shared service accounts), short-lived task-scoped and sender-constrained credentials issued by an Identity Broker, deny-by-default tool/API allowlisting enforced at a policy gateway, and an **append-only, tamper-evident Agent Activity Log** (e.g., a hash-chained log where `hash_i = sha256(hash_{i-1} || event_i)`) that reconstructs "what did this agent do, and on whose authority" independent of the model's own self-report ([Cloudflare: Agent Access Model](https://blog.cloudflare.com/the-agent-access-model/); [agentzt](https://github.com/Cubernet/agentzt)). This pattern applies as an external control-plane wrapper regardless of which of the four frameworks is used internally. Regulatory drivers cited for 2026: GDPR Art. 30 (processing register), EU AI Act Art. 12 (logging for high-risk systems), SOC 2 Type II, and 2025 SEC cybersecurity disclosure rules — with a claim that **7 in 10 enterprise AI deployments in 2026 ship without complete audit trails** ([teamazing: Audit Trail + RBAC Requirements](https://www.teamazing.com/blog/ai-agent-audit-trail-rbac-requirements/)).

> ⚠️ The "7 in 10" statistic is a single-source vendor claim without a disclosed survey methodology — treat as directional signal, not a validated industry figure.

## 5. Production Failure Modes

### 5.1 LangGraph — State Bloat, Checkpoint Races, and Silent Durability Loss

- **Checkpoint serialization bloat** (§2.2): 85% storage overhead, 37.8% token overhead from full-Pydantic serialization with no pluggable alternative as of the report ([Issue #7714](https://github.com/langchain-ai/langgraph/issues/7714)).
- **Silent mid-session durability loss (`langgraph dev`).** Checkpoints are only flushed to disk on a clean `close()`; a 10-second flush loop intended as a safety net was found to drop its own `PersistentDict` registrations on its first tick due to a filename-keyed overwrite bug. Net effect: a SIGKILL, crash, or machine sleep mid-session silently loses all state since the last graceful shutdown, while the run *appeared* healthy throughout — later reads of `/threads/{id}/state` return `500` with no prior error signal ([Issue #8298](https://github.com/langchain-ai/langgraph/issues/8298)).
- **Long tool-call re-dispatch / duplicate execution.** Tool calls exceeding ~180 seconds on LangGraph Cloud are silently re-dispatched from the last checkpoint by a stale-run sweep (`BG_JOB_HEARTBEAT` hardcoded) while the original execution is still in flight — both complete, causing **2–3× redundant work and cost**, with no application-level idempotency at the tool-call boundary by default. Maintainers confirmed this cannot be fixed without changing retry semantics that would break other behavior; the sanctioned fix is external idempotency fencing (§3.5) ([Issue #7417](https://github.com/langchain-ai/langgraph/issues/7417)).
- **Async-durability memory leak.** With the default `durability="async"`, each superstep submits a checkpoint write as a coroutine capturing a reference to the previous superstep's pending future, forming an unresolved chain that grows **O(N²)** in worst case when state accumulates per superstep (e.g., appending to a `messages` list). Confirmed in production by multiple reporters running 50–300-superstep multi-tenant graphs with `AsyncPostgresSaver`, observing linear pod memory growth over a run's lifetime. Workaround: `durability="sync"` (adds backpressure, ~3–5ms round-trip cost per step — acceptable against multi-second LLM turns) ([Issue #7094](https://github.com/langchain-ai/langgraph/issues/7094)).
- **Checkpoint bloat under tool-heavy workflows** (§2.4): every tool invocation triggers a full state snapshot even though most checkpoints are never used for recovery (transient failures like rate limits typically resolve within the same turn/retry). Workaround: wrap tool-heavy sequences in a subgraph with its own checkpoint namespace so the parent only checkpoints at subgraph boundaries (~70% checkpoint-count reduction), at the cost of coarser recovery granularity (a failure in tool 3 of 5 restarts the whole chain) ([The Colony](https://thecolony.cc/post/97ca6363-4d21-4862-aa67-782fbf71ff1f)).

### 5.2 OpenAI Agents SDK — Handoff Loops and the Tool-Choice Dilemma

- **`tool_choice="required"` infinite loops.** Multiple independently-reported GitHub issues describe agents stuck calling the same tool repeatedly until `max_turns` (even raised to 100) is exhausted, when `ModelSettings(tool_choice="required")` is combined with a single available tool — the model never "decides" it has gathered enough information to stop. The reported dilemma: `tool_choice` optional → model sometimes hallucinates an answer instead of calling the necessary tool; `tool_choice="required"` → model loops until token/turn budget exhaustion. No fully satisfying built-in resolution is documented; community workarounds include removing `tool_choice="required"` entirely or adding an explicit "call this tool at most once" instruction (with mixed reliability) ([Issue #191](https://github.com/openai/openai-agents-python/issues/191)).
- **Cycle amplification not caught by `max_turns`** (§2.3, §3.5): a legitimate two-agent handoff cycle can cost 3–6× a linear path while staying well under the turn cap, because `max_turns` counts LLM calls, not logical A→B→A cycles ([RunGuard](https://runguard.dev/blog/openai-agents-sdk-cost-control.html)).
- **Guardrail scope gaps.** Input guardrails apply *only* to the first agent in a handoff chain, and output guardrails only to the agent producing the final output — a handed-off agent mid-chain is **not** re-validated by the original input guardrail, and guardrails do not apply to the handoff tool-call itself. This is documented framework behavior, not a bug, but a common source of production surprise when teams assume guardrails apply uniformly across every agent in a multi-hop chain ([Handoffs Docs](https://openai.github.io/openai-agents-python/handoffs/)).

### 5.3 CrewAI — Role Confusion, Hallucinated Delegation, Model-Specific Parsing Bugs

- **"Coworker not found" delegation failures.** In hierarchical mode, the manager LLM frequently invents or mis-references a coworker name that doesn't match any agent in the crew (e.g., delegating to `"Directory Info Extractor"` when the actual agent is named `"directory document summarizer"`), raising a runtime tool error. Maintainers note this is disproportionately a **smaller-model problem** — recommending only stronger LLMs for hierarchical delegation. A separate root cause was identified where CrewAI's hierarchical tool injection incorrectly scoped the *task's* agent as the valid coworker set instead of the *crew's* full agent list when a `manager_agent` was also explicitly set on the task ([Issue #1399](https://github.com/crewAIInc/crewAI/issues/1399)).
- **Non-OpenAI model parsing/hallucination issues.** Multiple reports describe tool-output hallucination and malformed "Thought/Action" parsing specifically with Gemini and Claude models routed through CrewAI (via LiteLLM), while the same workflows are described as working reliably on GPT-4o/DeepSeek. Symptom: after a real tool call returns correct data, the agent's next "thought" block hallucinates additional, semantically-adjacent-but-fabricated content (e.g., inventing class names related to but absent from actual file contents) which then propagates into subsequent reasoning ([Issue #3095](https://github.com/crewAIInc/crewAI/issues/3095)). A related bug: Gemini tool-calling silently received `tools=null` in the underlying API request due to a CrewAI→LiteLLM conversion gap in v0.121.0 with LiteLLM v1.70.4 — the community workaround required subclassing the LLM wrapper to cache and re-inject tool definitions when the framework failed to pass them ([Issue #2895](https://github.com/crewAIInc/crewAI/issues/2895)).
- **Memory-induced quality degradation under retry storms.** A user running a business-proposal-generation crew with `memory=True` observed that repeated re-runs after `429` rate-limit errors caused progressive output degradation into unusable hallucinations, with no documented mechanism to select a memory "start point" or partially reset state — the only mitigation found was deleting the entire local memory store directory ([Issue #826](https://github.com/crewAIInc/crewAI/issues/826)).
- **Knowledge source misconfiguration causing fabrication.** `knowledge_sources` set at the `Task` level (unsupported — must be set at `Agent` or `Crew` level) silently fails to load, and the agent fabricates ("makes up") non-existent file contents and responses rather than raising a clear configuration error ([Issue #2233](https://github.com/crewAIInc/crewAI/issues/2233)).

### 5.4 Google ADK — Migration Breakage and Tool Co-existence Limits

- **ADK 1.x → 2.0 breaking changes are severe and under-tooled.** Storage is structurally incompatible across versions (data-loss risk if shared); the `run()` override contract changed (custom execution logic must move to `BeforeAgentCallback`/`AfterAgentCallback`); direct session-event appending is disallowed (events must be explicitly `yield`-ed for the framework to manage persistence/routing); and — critically — **broad `except Exception` or `except BaseException` blocks inside tools silently disable ADK 2.0's native automatic-retry mechanism** for that step, and catching `BaseException` specifically traps `NodeInterruptedError`, breaking the framework's ability to pause for human-in-the-loop input ([ADK 2.0 Migration Docs](https://github.com/google/adk-docs/blob/main/docs/2.0/index.md)).
- **No automated database migration tooling.** An open, long-unaddressed RFC documents recurring production pain: breaking schema changes shipped in ADK 1.14.0, 1.17.0, and 1.19.0 with no automated migration path, no Kubernetes-native migration hooks (teams must SSH into pods), race conditions when multiple pods attempt concurrent migrations with no locking, and no downgrade/rollback capability. A maintainer/community comment from mid-2026 states plainly: "I am shocked that it's almost June 2026 and we're still asking for a way to reliably migrate the database in production... It makes me scared to update ADK" ([ADK Issue #4387](https://github.com/google/adk-python/issues/4387)).
- **Tool co-existence restriction.** Certain built-in tools (Code Execution and Google Search with the Gemini API, Vertex AI Search) **cannot be combined with any other tool in the same agent** in ADK Python v1.15.0 and below — a workaround flag (`bypass_multi_tools_limit=True`) exists only for `GoogleSearchTool`/`VertexAiSearchTool`, and built-in tools generally cannot be used within a sub-agent at all (with that same narrow exception) ([ADK Tool Limitations](https://github.com/google/adk-docs/blob/5331a07f/docs/tools/limitations.md)).
- **Supply-chain incident.** ADK 2.0.0 stable explicitly excludes and pins around LiteLLM versions 1.82.7–1.82.8 following a compromised-package security incident — teams pinning older ADK-compatible LiteLLM versions were advised to audit immediately ([DEV Community: ADK 2.0 Migration](https://dev.to/peytongreen_dev/google-adk-20-is-now-stable-workflow-runtimes-breaking-changes-and-how-to-migrate-4ah8)).
- **Framework-acknowledged generic agent-loop risks** (motivating ADK 2.0's graph model): Google's own blog acknowledges that pre-2.0 autonomous ADK agents could "get stuck in infinite loops, bypass key business logic due to hallucinations, or fail without raising clean exceptions," and that appending every raw tool output directly to context causes **context bloat** that degrades attention and increases loop/redundant-execution risk over long-running tasks ([Why We Built ADK 2.0](https://developers.googleblog.com/why-we-built-adk-20/)).

### 5.5 Cross-Framework Failure Mode Comparison

| Framework | Signature failure mode | Root cause | Primary mitigation |
|---|---|---|---|
| LangGraph | State/checkpoint bloat; silent durability loss; duplicate tool execution on long calls | Full snapshot per superstep; async coroutine chains; heartbeat-based stale-run detection | `durability="sync"`; subgraph checkpoint namespacing; external idempotency fencing; Temporal integration |
| OpenAI Agents SDK | Handoff/tool-call infinite loops; cycle cost amplification hidden from `max_turns` | Model-driven routing has no structural cycle limit; `tool_choice="required"` removes the model's "stop" option | Custom cycle-detection wrapper (`RunGuard`-style); avoid blanket `tool_choice="required"`; `error_handlers["max_turns"]` |
| Google ADK | Breaking migrations losing state; silent retry-mechanism disablement; tool co-existence restrictions | Version-to-version schema incompatibility; broad exception handling masking framework-native retries | Isolated storage per version; propagate exceptions instead of catching broadly; `bypass_multi_tools_limit` |
| CrewAI | Role/coworker confusion; non-OpenAI model tool-parsing hallucination; memory-driven quality decay | LLM-driven delegation with no static verification of coworker names; LiteLLM translation gaps for non-OpenAI providers | Use frontier models for hierarchical mode; pin/patch LiteLLM tool-conversion; periodic memory reset |

### 6.2 Trade-off Matrix

| Dimension | LangGraph | OpenAI Agents SDK | Google ADK | CrewAI |

### 6.3 Capacity Planning Reference (Google ADK / Vertex AI Agent Engine)

Google's published formula for sizing Agent Platform quotas, using example variables `peak_users=250`, `avg_requests_per_user_per_min=2`:

- **Query QPM** = `peak_users × avg_req/min` = `250 × 2 = 500` → recommended with 50% buffer: **750 QPM**
- **Session-event-append rate** = `Query QPM × events_per_request` (a single query can generate ~12 events: LLM call → tool-use decision → tool execution → tool-result LLM call → final response) = `500 × 12 = 6,000/min` → buffered: **9,000/min**
- **Session writes/min** ≈ Query QPM (typically ≤ query rate) → buffered: **750/min**
- **Concurrent `BidiStreamQuery` connections**: hard-capped at **10/min** regardless of buffer — a structural ceiling that must be architected around (e.g., connection pooling/multiplexing) rather than requested away, for any real-time bidirectional-streaming ADK deployment at scale ([Google Cloud Agent Quotas](https://docs.cloud.google.com/gemini-enterprise-agent-platform/resources/agent-quotas)).

This is the only framework among the four with a **publicly documented, formula-driven capacity-planning methodology** tied to a managed deployment target — LangGraph Platform, OpenAI's Runner, and CrewAI's Crew/Flow runtime rely on generic LLM-provider rate limits plus self-managed infrastructure sizing, without an equivalent vendor-published planning worksheet in the sources consulted.
